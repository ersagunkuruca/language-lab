Shaders: the language on the GPU

Each picture below is a program in the language. It says what colour the point (x, y) is at a given time, either as one definition colour that gives a Colour record, or as three definitions red, green and blue. The compiler turns that into WGSL, WebGPU's shading language, and the GPU runs it once for every pixel, every frame.

Only part of the language can go to a GPU: Numbers and Bools, records of them, arithmetic, if, lets, and calls. There is no recursion, because a GPU has no call stack. A function that calls itself as its last step is fine, though, because that is a loop, and it becomes one. Anything else is refused, and the compiler says why, the way it reports a type error.

A ray marcher, with normals from the derivative

Starting…

For each pixel, march follows a ray from the camera. scene says how far the nearest surface is, so the ray can safely step that far, and then it asks again. Where a surface faces is the gradient of scene. Most ray marchers estimate it by sampling scene at six nearby points. Here it is exact: shade asks for unit(gradient((q) ↦ scene(q, time))(p)), the slope of scene along each axis as one Vec, and the compiler generates the gradient's code from scene before printing the shader, so it runs on the GPU like everything else and follows any edit to scene. (Differentiating a program before compiling it for a GPU is what Enzyme does.) march and shadow call themselves as their last step, so on the GPU they are loops.

The WGSL the GPU runs

On the left is the WGSL the compiler printed. A Number is f32, a record is a struct, a let is a let, and an if is an if statement. Calls stay calls. On the right is the part the page adds around it: one triangle that covers the screen, and a fragment shader that turns each pixel's position into x and y and calls the program.
