# Second review: after shaders, folds and web apps

Written 2026-10-22, evening, at `2edfddc` (after PR #108). It follows
[REVIEW.md](REVIEW.md), the morning's review, and works the same way: the
docs were read, every suite was run, and the holes below were found by
trying to break things. The ones that fit in a few lines are todo tests
(`test/known-holes.test.ts`, "R2" at the end, and
`compiler/test/known-holes.test.ts`): they run, they fail today, and they
don't fail the suite. Nothing is fixed in this PR.

What was run, all green: projectional 174 tests, compiler 44, invertible
35, the editor smoke test (101 definitions, and 16 saved by an older
editor), the shader smoke test (both with and without WebGPU), and the
GPU check (768 values against the evaluator, 0 wrong).

## The verdict, first

The day went well. Every hole the first review could show in a test is
closed: all seven of its todo tests pass. Shaders, folds-as-representations
and web apps landed as designed, each with a doc written first and tests
that pit the evaluator against the compiled code.

Three things stand out now:

1. **The type knows, and the consumer doesn't ask.** The browser freeze
   Ersagun hit, the effect hole fixed in #102, and two holes found today
   are one bug class. An effect is in a row, and some piece of machinery
   (the shader profile, the Cells handler, a data field) removes it
   without handling it. The first review fixed the checker. The new
   machinery since then (profiles, cells, pages) was never held to the
   same rule. §1.
2. **Equality still has two meanings, and the fix for Int made a third.**
   `equal(1e12, 1e12 + 1)` on Numbers is `true`. The same comparison
   through a generic `same(x, y) = equal(x, y)` is `false`. Run backwards,
   Ints still compare to within 1e-9. The first review asked for exact
   equality everywhere, with tolerance only where it's asked for. That
   wasn't done, and this is the result. §2.
3. **The editor is still not where programs are written.** Every program
   bigger than insertion sort (calc, wc, raymarch, the converter) was
   generated by the TypeScript DSL and then frozen as JSON. The
   "can't edit" items in the QA report that block real programs are all
   still open (inner lambda parameters, swapping a call's function,
   statement order). Of the four legs (regular programs, shaders, web,
   mobile), the weakest isn't a target. It's writing the program. §5.

## 1. The type knows, and the consumer doesn't ask

### 1.1 What happened

| bug | the effect | where it was dropped |
|---|---|---|
| #102: a printing function kept in a data field, called under `Choice` | `Console` | `infer.ts` gave a function type inside a data type a fresh row on every use |
| the GPU freeze | `Diverge` on `shadow` | `compiler/src/scalar.ts` filters `Diverge` out of the row ("Diverge is allowed: it just runs") |
| **new:** a formula that never ends | `Diverge` | `std.ts`: `formula` accepts `() -[Cells, Diverge]-> a`, and `read` is `(Cell a) -[Cells]-> a` |

**The shader.** `shadow` in `examples/raymarch` stops only when it touches a
surface or has travelled past 6 units. A ray that grazes a surface takes
tiny steps. If `scene` gives NaN, neither test is ever true and it never
stops. (`march` counts its steps and gives up after 120, so it is fine.)
Both carry `Diverge`, so the type can't tell them apart, and the profile
doesn't look anyway. On a GPU, a loop that never ends doesn't throw. It
hangs the tab or makes the browser reset the device.

The preview makes it worse. `editor/picture.ts` submits a frame on every
`requestAnimationFrame` without waiting for the last one
(`queue.onSubmittedWorkDone`) and doesn't watch `device.lost`. Once a frame
takes longer than a display refresh, work piles up. That fits "renders and
animates, then freezes after a few seconds", even for frames that do end.
That part is a hypothesis from reading the code. It hasn't been reproduced,
because the container has no GPU.

Two other symptoms Ersagun reported are not language bugs:

- **"Stops after the first frame" on the CPU.** This is by design: the
  evaluator draws one 64×64 frame in about 4 s, and the status line says
  so (shader smoke output). It reads as broken, so the message or the
  behaviour should change.
- **GPU found on one load and not on the next.** `requestAdapter()` is
  called once with no retry. Headless runs here always got the same
  answer, so this needs a real browser to chase.

**Cells.** LANGUAGE.md does say "`Cells` covers `Diverge` inside formulas
… so `read` can loop", but the error table says non-termination is
*inferred*, with no exception. A page's `main` is
`() -[Cells, Files, Abort]-> Html`. `Html`'s `text` and `part` take
diverging functions, so the page can hang, and nothing in its type says
so. The todo test builds `main = print(show(read(formula(() => spin(0)))))`,
which runs forever and is typed `() -[Cells, Console]-> Unit`.

### 1.2 The systematic check that would have caught all three

The checker is sound only if every place that *removes* an effect from a
row is a handler with a stated rule. Today there are more of those places
than handlers:

| removes | where | rule today |
|---|---|---|
| `Choice` | `first`, `all`, `count`, `optional`, `solve` | handlers ✓ |
| `Diverge` | `with fuel` | handler ✓ |
| `Diverge` | the scalar/WGSL profile | **dropped** |
| `Diverge` | `read` of a formula | **dropped** |
| `Cells`, `Update`, world | the runtime at `main` and at page mount | `mainProblem` / `pageProblem` ✓ |
| any | a function stored in data | fixed in #102 (closed row) |
| `Diverge` | a representation's fold (NUMBERS.md: effects should come from the meaning) | not checked |

Two things would keep this table true:

- **A ledger in code.** Every place that filters an effect out of a row
  calls one function, `discharge(effect, why)`, and a test lists the calls
  and compares them with the table above. Adding a profile or a runtime
  handler then means adding a row on purpose.
- **A container matrix test.** For each place a function can hide (data
  field, cell, formula, `Html` part, `on` handler, a shader, a `solve`
  body, a representation's job, a module's pinned export), put in a
  function that does each effect (`Console`, `Choice`, `Diverge`, `Update`)
  and check that the effect either reaches the outer row or is refused.
  That is 9 × 4 small programs, generated, not written by hand. #102 and
  both new holes are cells of that matrix.

The shader also needs a **soak test**. The shader smoke test checks that the
first frame draws. A frame loop that hangs after a few seconds needs
"run 10 s, every frame done within its budget". In headless Chrome with
SwiftShader that is slow but it works.

## 2. Equality: one operation, several meanings

The first review (§1.3) found two meanings: exact forward, near
backwards. The recommendation was exact everywhere, and a `near` relation
only where tolerance is wanted. GAPS.md G0 found the Int case and fixed it
*type-directed*: the checker records at each `equal` whether the type has
only Ints (exact), only Numbers (near), or a type variable (exact on whole
numbers, near on the rest). That fixed the case it was asked about and
made two more:

- **Abstraction changes answers.** `equal(1000000000000, 1000000000001)`
  on Numbers is `true`. `same(x, y) = equal(x, y)` on the same two numbers
  is `false`, because inside `same` the type is a variable. Inlining a
  definition, a refactoring the editor will want to offer, changes the
  program's output. (todo: R2 §1.2 generic)
- **Backwards was missed.** `relate.ts`'s `unify` calls `close` for every
  pair of numbers, Int or not. So `f() = one of([1000000000001])` run
  backwards with result `1000000000000` has an answer. Forward, the same
  equation is false. (todo: R2 §1.2 backwards)
- And still from the first review: `show(0.1 + 0.2)` is `"0.3"`, so `show`
  isn't injective on Numbers, and the converter's "show run backwards is
  the parser" accepts only rounded spellings.

**What class of bug this is.** G0 was found only because a person wrote
the ideal JS by hand. The differential tests compare evaluator with
compiled, and both had the same bug. Same-meaning tests can't find a wrong
meaning. **The systematic check** is laws, not agreement:

- `equal` is an equivalence on every type: reflexive, symmetric and
  *transitive*. Near equality isn't transitive, so a property test over
  boundary values (2^53 ± 1, 1e12, −0, NaN, 0.1 + 0.2, a surrogate pair)
  fails at once.
- Forward and backwards agree: for every example function `f` and inputs
  `x`, `relate(f, x)` gives exactly `f(x)`, and `relate(f, out = f(x))`
  includes `x`. This one test would have caught the backwards Int bug,
  the non-termination in §3, and the reason the converter needs
  `show` to round-trip.
- Inlining preserves meaning: for each example, inline every non-recursive
  call and compare outputs.

**Fix.** Do what the first review said. `equal` is exact on every type, in
all three places (`run.ts`, `relate.ts`, the compiler). `near(a, b)` is an
ordinary prelude function for Numbers. The equation solver keeps its own
tolerance internally (it really is numeric), but the results it hands back
are compared exactly. `show` prints the shortest round-tripping decimal.
Examples that relied on near equality will show up as failing tests, and
that's the point.

## 3. Running backwards can fail to end on a finite program

`f() = one of([3])`, run with result 5, never finishes. With result 3 it
gives its answer and then keeps searching. Without a budget it fills
memory (it was killed after 104 s in the probe). The cause is the order of
goals: `member` (`relate.ts`, `one of` backwards) runs before the list
literal's `cons` calls have bound its argument. So it sees an unknown list
and enumerates every list that could contain 5: `[5]`, `[_, 5]`, … none of
which unify with the real list. This is the classic miniKanren
goal-ordering divergence.

This matters more since this morning. The converter runs a function
backwards on every keystroke, and "invalid input" is shown when the search
says no answer. A search that doesn't say "no" is a hung page. Run
backwards, there is no `Diverge` to warn anyone. The direction's
termination isn't in any type.

**Fix, small:** `member` waits until its list is known, the way `first`
and `all` already do ("aggregate" in `relate.ts`). **Fix, real:** the mode
analysis both reviews asked for (REVIEW.md §1.2, ROADMAP "still open").
Order the goals per direction, statically, so that constructors and known
inputs come first, and say per direction whether it ends. (todo: R2 §2.1)

## 4. Hand-kept tables drift

**#104** (a saved program that solves a function couldn't be reopened)
came from `modules.ts`'s `pointsAt`, a hand-written list of which fields
of each node kind hold ids. It read a solve's port name `out` as a node.
**#102** was the same shape: when effect rows came to function types, the
path for function types *inside data* was one of the places that wasn't
updated.

The same risk is bigger for builtins. One builtin like `sqrt` is described
in up to eleven files: its type and its forward run (`prelude.ts`,
`std.ts`), backwards (`relate.ts`), its derivative (`derive.ts`), its unit
rule (`units.ts`), JS (`compile.ts`), the compiler's relation fallback
(`relation.ts`), the scalar profile (`scalar.ts`), WASM (`wasm.ts`), WGSL
(`wgsl.ts`), and the editor (`main.ts`). There are 45 builtin cases in
`compile.ts`, 30 in `run.ts` and 17 in `relate.ts`. When a builtin gets a
new meaning, nothing says which of the eleven missed it.

**Systematic check.**

- One record per builtin (type, forward, backwards rule, derivative, unit
  rule, JS, WGSL, cost), with every table derived from those records. A
  test fails if a builtin lacks an entry for a job without saying "not
  supported, because …".
- `pointsAt` derived from one schema of node kinds, which says for each
  field whether it is an id, a list of ids, or a map whose *keys* are
  ports.
- A round-trip test over every example: save in the editor's file format,
  open, check, and compare the code, the names and every side table. Run
  it again on each example after a random edit from the palette. #104 was
  exactly this test, run by a person.

## 5. Uniformity, and where complexity is creeping in

What holds up well:

- **Folds-as-representations made one mechanism out of three.** The
  compiler's loop, the text fold and the counted fold are rows of one
  table, and Peano `Nat` on Ints is written in the language. This is the
  uniformity rule working.
- **`Html` is three variants of an ordinary type.** Widgets are
  functions, and nothing in the language knows HTML. The shader refusals
  are one lowering (`scalar.ts`) printed twice (WASM, WGSL), each refusal
  with a reason.

Where it is slipping:

- **Two page models.** `src/lang/ui.ts`'s `UI` type (`text`, `button`,
  `entry`, `slider`, `row`, `column`, `dynamic`) still drives
  reactive.html, next to std's `Html`. WEB.md says the old one goes in its
  own PR. Until then there are two ways to make a page, and they mount
  differently.
- **The `on` handler's row is closed and hand-picked:**
  `[Cells, Update, Console, Files, Abort]`. Adding time, randomness or
  HTTP means editing std's `Html` type, and so does a user's own effect
  handled at the page. A named row ("what a page may do") defined once,
  or an open row checked by `pageProblem`, would keep `Html` fixed as
  effects grow.
- **Profiles live in the compiler, not the checker.** The first review
  (§5.2) proposed targets as profiles inferred like effects and shown in
  the editor ("this runs on the GPU"). What exists is a compiler pass that
  refuses with reasons. That is useful, but it's a second checker with
  its own idea of effects, which is how §1's `Diverge` slipped through.
- **Fuel still means two things.** COMPILER.md, "Diverge and fuel":
  running out inside plain code abandons the whole `with fuel` body when
  compiled, while the evaluator lets a later branch go on. This has been
  known since this morning and is unchanged.
- **Leftovers.** `examples/compose` and `examples/quadratic` are untyped
  pre-typed-core programs with 32-bit ids, kept for `src/demo.ts`.
  `lab check examples/compose` reports six errors, and quadratic's
  definitions have no names. Either retire them or mark them as archive.

## 7. The four legs

| leg | where it stands | weakest point |
|---|---|---|
| **Regular programs** | strongest: calc (27 definitions), wc, `lab run`/`compile`/`check`, one bundled file, buffered output, a 1 GB stack, folds as loops, Int that never overflows | no time, randomness, HTTP, environment, `Map`/`Set` or arrays; compiled calc is still 1.5× the ideal |
| **Shaders** | the scalar profile to WGSL and WASM, records as structs, an SDF ray marcher with normals from `derivative`, checked on a GPU in CI | scalar only (no `vec3`, no `Float32`); loops not bounded (§1); the live preview hangs |
| **Web** | `Html` in std, Solid-style mount for both evaluator and compiled code, a browser world, one-file output, the converter | one demo; 205 KB for ten fields (the solver ships so binding can run backwards); no timers or HTTP, so no real app (no fetch, no clock, no animation); no keyed lists; backwards search can hang (§3) |
| **Mobile** | nothing, by design (packaging of the web leg) | inherits everything web lacks; touch editing untried (QA: phone width) |

**On course?** Yes for the language. It is gaining real features without
new node kinds, and the morning's holes are closed. But the next target
(WASM, then native) would be a fifth leg on a body that can't yet be
*written* in its own editor. **The weakest leg is authoring.** No program
larger than insertion sort has been written in the editor. The QA pass's
"can't edit" list is untouched, and the "bigger program" practice (GAPS.md)
writes its programs in TypeScript. That's practical, but it means the
editor is never what's being stressed. The next bigger program (GAPS round
2) should be written in the editor, with the TypeScript DSL off-limits,
and everything that hurts becomes the editor queue.

Among the targets, the weakest is web, for want of three world effects
(time, randomness, HTTP). Those are also the regular-programs leg's main
gap, so one series of PRs serves both.

## 9. Recommended fix order

One PR each, bugs first, per the step-by-step rule:

1. **The freeze (§1).** (a) `shadow` gets a step limit, as `march` has.
   (b) The preview waits for the previous frame before submitting the next
   one, and handles `device.lost`. (c) The CPU fallback's one frame says so
   plainly, or keeps drawing slowly. (a) is an example change. (b) and (c)
   are editor changes, already queued in the editor thread.
2. **The shader profile refuses `Diverge`** unless the loop is bounded in
