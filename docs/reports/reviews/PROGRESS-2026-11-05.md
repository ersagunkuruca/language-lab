# Is progress slowing down? 2026-11-05

Written 2026-11-05 at `3ff5fcdc` (after PR #1892), during the 2-hour run, at
Ersagun's ask: "it feels like everything is slowing down by the minute and
we are not getting closer to achieving some of our goals. Is the complexity
of the codebase increasing too much? Is this an architecture problem? Are we
gonna need a rewrite or a refactor?"

Nothing is changed here; no code was touched. Numbers come from git on
`origin/main` (commands in "Method" at the end), BACKLOG.md, DONE.md and the
run counts the coordinator posted.

## The answer, first

1. **The work itself is not slowing down. The meter is.** PRs per hour have
   almost doubled since yesterday (12.6 an hour in the 12-hour run, 23 an
   hour in the last two runs), and a step takes a median of 6 minutes. What
   fell is *top-level rows closed* (49, then 23, then about 4, then about 2),
   because the small rows are gone. The 57 rows left are mostly epics: the
   five biggest have taken 31 to 61 PRs each and are still open.
2. **But too much of that speed goes sideways, for two reasons.** One is
   architecture: each language feature is still built about five times, once
   per way of running a program, and the retirement of the second JavaScript
   compiler has taken 61 PRs without making it any smaller. The other is
   scope: much of the work goes to breadth (Unicode collation, JSON grammars,
   an error table, exact reals) while some stated goals have no rows at all
   (mobile) or have stood still for days (shaders, lists as arrays).
3. **No rewrite. A short, targeted refactor, plus a change in what we
   count.** The foundations were judged sound two days ago and the three
   worst problems found then have been fixed. A rewrite would throw away
   85,000 lines and, with the same way of working, grow the same sprawl. The
   refactor is: finish one compiler path with a hard cutoff, stop keeping
   every target at parity with every feature, and steer by goal milestones
   instead of row counts. Details in "Recommendation".

## 2. Is complexity the cause? Partly, and in one specific place

### Size

About 8,000 lines a day. That alone isn't alarming for a project this
young and this fast; what matters is whether a change has to touch more
places as it grows. In one place it does.

### The same meaning, written about five times

FOUNDATIONS-2026-11-03 §2 found "the language's meaning written about six
times". Two days later the count is unchanged. L213 (files and resources as
handlers) is a clean example from today: 20 PRs, of which one set built it
in the evaluator and the core IR, and the rest ported the *same* feature to
each way of running:

- compile.ts (L213a5), JavaScript from the core IR (L213b3, b4, c3, c6),
- C (L213a6, c4, c5, c7), WebAssembly (L213a7, c8, c9).

Across all 447 PRs since 11-04 07:00, about 100 (22%) name a target in the
title (on C, WebAssembly, compiled, core IR, compile.ts, JavaScript). Each
new feature costs roughly one PR per target, plus the tests for each, and
the number of targets only grows.

### The migration that doesn't finish

C137 says compile.ts is to be retired and that "nothing new goes in here
alone". After 61 PRs:

| file | 11-03 | now |
|---|---|---|
| compiler/src/compile.ts (old JS path) | 3,477 | 3,527 |
| compiler/src/scalar.ts (core IR) | 2,540 | 3,101 |
| compiler/src/core-js.ts (new JS printer) | 416 | 864 |

The new path grew; the old one didn't shrink. compile.ts still gets new
features (L213a5, a handler's release) so that it stays at parity, 79
test files import it, and the editor still falls back to it
(editor/pageCompile.ts, editor/runWorker.ts). A migration with no cutoff
date is a permanent second implementation: every feature pays twice for as
long as it lasts.

### What is *not* the problem

The foundations review's other findings were acted on: the node schema and
hash (L178), splitting std.ts's signatures from its code (L180), checking
the library once per process (L216, full unit run 35-40 min → about 15),
lists as arrays inside the representation layer (C138), the per-group check
cache (L183), main.ts split (E228). The model is still small and flat; the
checker, the core IR and the representation layer are the right shapes.
Nothing here points at a foundation that has to be replaced.

The lanes pick by priority (bugs, special cases, editor, language, then
targets). That order is right for health, but nothing in it ever pulls a
*goal* forward: mobile and shaders are "more targets", which comes last, so
they never come up. Meanwhile L-rows of breadth (Unicode collation and
Greek casing in L214, JSON as a grammar in L72, an error table in L187,
real sin and exp in L88) are "language" and come first. Each is reasonable
alone; together they are most of the Language lane's last two days.

## Recommendation: refactor, targeted, and steer by goals

**No rewrite.** The problems are a migration left half done and a backlog
that doesn't point at the goals. A rewrite fixes neither.

**1. Finish C137 with a cutoff (one Compiler-lane block, P1).**
Freeze compile.ts now: no feature PRs go into it, even for parity. Move
the tests that import it to the core IR, move the editor's fallback, then
delete it. Where an example doesn't lower yet, it runs in the evaluator
until it does, rather than through compile.ts. Count this done when
`compiler/src/compile.ts` no longer exists.

**2. Stop porting every feature to every target at once.**
Name two tiers. Tier 1 (always at parity): the evaluator, which is the
meaning, and JavaScript from the core IR. Tier 2 (C, WebAssembly, WGSL):
a feature reaches them through the shared core IR when it can, and through
target-specific runtime work only when a goal milestone needs it. The
L213 pattern (each feature ported by hand to C and WebAssembly in the same
day) stops being the default.

**3. Steer by goal milestones, not row counts.**
Keep the lanes and steps, but each run names one goal milestone it serves,
with a demo you can see. For example: "a shader program written in Ters
runs on the GPU from the editor", "lists stored as arrays everywhere by
default, on every tier-1 target", "first mobile build". Report per run:
steps done, milestones reached, and lines removed vs added. Rows of
breadth that serve no milestone (most of the 39 P3 rows) are parked, not
deleted.

**4. Rows say what's left (cheap, do it first).**
Trim each row to the open part and a link; history goes to DONE.md. C137,
T7, I167, C93, L187 first. This cuts what every lane reads every step.

Order: 4, then 1, then 2 and 3 together. 1 is the only one that is real
code work: moving 79 test files and two editor callers, then deleting
3,527 lines. Split it into steps before the run, as with any big row.

## Method

- PRs per run: `git log origin/main --since=… --until=… --format=%s | wc -l`
  for each run's window.
- Lines: `git ls-tree -r --name-only <commit> -- <dirs>`, `.ts`/`.js`
  files, summed with `git cat-file -p | wc -l`, at the last commit before
  2026-11-03 07:00 and at `origin/main`.
- Rows' PRs: subjects starting with the row id; opened = first commit
  adding `| <id> |` (`git log -S`).
- Target-naming PRs: subjects since 2026-11-04 07:00 matching on C, in C,
  WebAssembly, wasm, compiled, core IR, compile.ts, JavaScript, JS.
- Row sizes: characters per `| <id> |` line of BACKLOG.md.
- Rows closed per run: the coordinator's counts in the count thread.
