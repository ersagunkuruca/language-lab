# Seventh review: the editor

*Superseded (2026-11-02):* the latest whole-project review is [REVIEW-2026-11-02c.md](REVIEW-2026-11-02c.md). This one stays as written.

Written 2026-11-02 (morning UTC) at `214c5a3` (after PR #1078), a critical
review of the editor (`editor/`), asked for by the coordinator to refill
the Editor lane during Ersagun's "as many tasks as you can" run. The last
three reviews ([R4](REVIEW-2026-11-01.md), [R5](REVIEW-2026-11-01b.md),
[R6](REVIEW-2026-11-02.md)) looked at the language, the library and the
compiler; this one looks only at the editor. The daily QA passes
(latest [QA-2026-11-02b](../qa/QA-2026-11-02b.md), all its rows done) click
through every example; this review instead reads the code and measures
what QA doesn't: saving, memory, the cost of a click and of an edit on the
big examples, a phone, and what the language has that no gesture can make.

Nothing is fixed in this PR and no code is touched. Each finding has a
repro and a row in BACKLOG.md (Editor lane, E197 to E207), ranked bugs
first.

**How it was measured:** the built page (`npm run build-editor`) in
headless Chromium through Playwright, 1600×1000, on this container's
machine; the phone runs are a Pixel 7 profile with the CPU slowed 4×.
Times are wall-clock around one synchronous click or key in the page, so
they include the redraw. A CPU profile (an unminified build) split the
slow ones. Probe scripts are short and quoted where it matters.

## The verdict, first

The editor is sturdy: no page error in any probe, on any of the five
largest examples, desktop or phone, and the phone layout has no sideways
scroll. Every edit is still a typed tree edit with its reason when it's
refused, and the loose-parts design holds. The weak spots are not in the
editing model but around it:

1. **Your work stops being saved, silently.** Each saved program carries
   its own copy of the whole library, 1.46 M characters, so the browser's
   storage is full at about three programs. The third program of your
   own is never saved, with no message, and the guide promises "Every
   edit is kept in this browser". §1.
2. **The language has outgrown the gestures.** A data type or an effect
   made in the editor can't have a type parameter, so `Tree a`,
   `Stack a` or `State s` can't be written there, while nearly every type
   in the library is generic. Private constructors, ways, costs and
   directions have no gesture either. §2.
3. **Everything is redrawn on every click, and an edit re-checks and
   re-offers everything.** A click that only selects costs 100 to 210 ms
   on the big examples (200 to 330 ms on a slowed phone); a delete in
   Constructions or Bounce costs 1.3 to 2 s, more than half of it working
   out the palette for the hole the delete leaves. Undo keeps every
   version with its caches: 5 MB more per edit, without limit. §3, §4.

## 1. Saving fails silently from about the third program on (E197)

`save()` (main.ts) writes every program you have touched to one
localStorage key:

```ts
try { localStorage.setItem(STORE, JSON.stringify({ current: doc.program, docs, held })); } catch {}
```

and a doc's `code` is `merge(BASE, code)`: the program on top of the whole
library (`LIBRARY.code`, 10,456 nodes, **1,463,649 characters** as JSON).
`onToday` throws that copy away on load and puts today's library under the
program's own nodes, so the copy is never read; it is only written. A
browser keeps about 5 M characters per site.

Repro (clean storage, the built page):

- Make new programs with **+ New program**, nothing in them. After the
  first, the store holds 2.98 M characters (the example you were on, plus
  yours); after the second, 4.44 M. **The third and every later one is
  never saved**: the store stays at 4,442,685 characters and still lists
  two programs of yours. Reload and the third is gone. No message.
- Or edit examples: one Delete in Constructions (2.18 M), one in Bounce
  (4.11 M), one in Spacetime: the store doesn't change, the Spacetime edit
  is lost on reload.

The empty `catch {}` hides it, and two docs say the opposite:
docs/learn/GUIDE.md §10 "**Every edit is kept in this browser** as you
make it", and docs/learn/TUTORIAL.md §3.6 "Every edit is kept in the
browser as you go."

**Fix, in order:** save only a program's own nodes (what a file already
holds: `userCode`/`own` filter, the library re-merged by `onToday`, which
already does it); then, when `setItem` still throws, say so on the status
line and point at **Save file**, rather than nothing. With the library
gone, the three biggest examples edited together are ~2.6 M characters.

## 2. No type parameters for types made in the editor (E198)

`Top.newDefinition` (ters/src/lang/toplevel.ts) makes a data type as
`{ kind: "typedef", params: [], … }` and an effect the same way; nothing in
toplevel.ts, editor/typed.ts or main.ts adds a parameter afterwards (no
"type parameter" anywhere in the three). A field's type picker
(`typeHeads`) does offer "the type's own parameters", but there are never
any. So the editor can't write:

- a generic container (`Tree a`, `Stack a`, `Queue a`, a `Result e a`);
- an effect with a parameter (`State s`, `Yield a`), which the language
  has had since L56;
- an operation's own type variable (L71a, `await : Ticket a → a`).

Meanwhile `Optional`, `List`, `Map`, `Tuple2`, `Ticket` and the effects
above are all generic in the library, so a program in the editor can use
them but can't make one. This is "what lets programs be written in the
editor", the lane's third priority, and a real one: round 7 and round 8
were written in the editor and only got away with it because their types
are concrete.

**Fix:** "Add a type parameter" (and remove, rename) on a data type, an
effect and an operation, the same way inputs are added to a function
(`addParameter`), with the field picker then offering it. Uses of the type
get a hole-like unknown argument (`Stack □`) to fill, or `a` where inference
can say.

## 3. Language features with no gesture (E199)

By reading toplevel.ts, typed.ts and main.ts for each node property in
ters/src/model.ts:

| what | language | gesture |
|---|---|---|
| a private constructor (`variant.private`, L79) | yes | none |
| a definition as one way of an interface field (`def.way`, WAYS.md) and its cost (`def.cost`) | yes | none |
| a definition that computes another direction of one (`def.direction`, POLAR.md) | yes | none |
| `unique` on a type (two types of one shape kept apart) | yes | none |
| an operation's `returns` and `later` | yes | yes (setReturns, setLater) |

These can be loaded from the examples and the library and are drawn, but
only text (the DSL, `lab`) can make or change them. Not all of them need a
button: a design note for the lane should say which belong in the
editor (private and ways look like yes; `unique` may stay a library-only
thing) and the rest go in as one row each.

## 4. Every click redraws everything (E200)

`select()` sets `ui.selected` and calls `render()`, which rebuilds the
whole app with `replaceChildren`: header, navigator, the graph's SVG, the
Blocks text, the Run panel and the inspector. Measured, one click on a
part in the Blocks pane, selection only (desktop):

| example | ms per click (three parts) |
|---|---|
| Numbers & physics | 135, 103, 115 |
| Tumble | 166, 142, 102 |
| Constructions | 212, 170, 131 |
| Bounce | 125, 209, 112 |
| Spacetime | 443 (first), 72, 63 |

On the phone profile at 4× CPU: 332 ms (Numbers), 197 ms (Spacetime). Over
100 ms reads as lag, and it's every click, arrow and Tab.

A profile of one click in Bounce (376 ms under the profiler) puts 170 ms in
`typedInspector`, of which ~100 ms is `Top.moveStep` run twice (main.ts
1767 and 2894) only to decide whether **Step earlier** and **Step later**
are enabled, and ~120 ms in `parentOf` (ters/src/model.ts), which scans
every node of the program (15,658 in Constructions) on each call; main.ts
and typed.ts call it from 19 places. The graph was 57 ms.

**Fix:** a parent index per version of the code (a WeakMap on `Code`, like
`calledDefs`), used by `parentOf`'s callers; "can this step move" as a
cheap look at the step's neighbours, not a whole edit; then, separately,
a selection change that redraws only the parts that show the selection.

## 5. An edit in a big example costs 1.3 to 2 s (E201)

One Delete on a part (desktop): Constructions 1.3 to 1.7 s, Bounce 1.9 s,
Spacetime 0.9 s. The profile of Bounce's (1.9 s): `applyT` 1.39 s, of
which the whole program's inference in `guardTyped` ~0.5 s; then the
redraw 1.16 s, of which **`fillPalette` 0.83 s**: Delete leaves a hole and
selects it, so the inspector works out every filling the hole could take
(`fillingsAt`, a mode check per candidate) before anything is drawn, even
when you were about to click elsewhere. Saving was 50 ms of it.

**Fix:** draw first, then the palette: show the Selected panel with its
type and a "working out what fits…" line, and fill the list after the
frame (or on the first keystroke into its search). The inference is the
Language lane's (infer.ts) and stays in E103's line.

## 6. Undo keeps everything (E202)

`commit()` pushes the whole previous `Doc` onto `undo`, which has no
limit, and the per-version caches (`mainRuns`, `traces`, `calledSets`…)
are WeakMaps keyed by `Code`, so a version in the undo list keeps its
caches alive too. Twenty Deletes in Constructions, heap after a forced
GC: 70 → 90 → 112 → 140 → 168 MB, **about 5 MB per edit**. An hour's
editing of a big program is a gigabyte; a phone's browser kills the tab
first, and with §1 nothing may be saved.

**Fix:** cap the undo list (a few hundred steps), and keep caches only for
the version shown (one `Code` at a time, or drop them on `commit`).

## 7. On a phone, a tapped part's type is out of sight (E203)

At phone width the editor shows one pane at a time: Programs, Graph,
Text, Run. Tapping a part in Text or Graph selects it, but its type and
its Selected panel are in the side column, which is the pane named **Run**
(it holds Run, Selected, Program, Checks, Files and Guide). `select()`
switches there only for a hole. The opening line on a touch screen says
"Tap anything to select it and see its type", and the status line keeps
saying it after the tap; there is no hover to show a title.

**Fix:** on a touch screen, a selection puts its kind and type on the
status line ("call of rotate : (Float64, Float64, Float64) → …", as the
hover title does), and the pane button reads "Run & more" or the side
pane gets a better name. The menu (long press) already works there.

## 8. The page is 25 MB (E204)

`index.html` is 25,072,751 bytes, 4,051,311 gzipped: the editor, the
library and every example's code.json (Spacetime alone 1.1 MB,
Constructions 0.9 MB) inlined, all parsed before the first drawing. To the
first graph: 3 to 4 s on this machine from disk, 9 to 12 s with the CPU
slowed 4×, before any network. The examples could be separate JSON files
loaded when picked (the site serves the repository anyway), and the page
would carry only the one it opens with.

## 9. Examples wired by hand; main.ts carries the state (E205)

Adding an example to the editor means: ~4 JSON imports at the top of
main.ts (80 now), an arm in `initialFor`'s 21-way conditional, an entry in
`EXAMPLES`, sometimes one in `START`, and for a page another list in
editor/build.ts. One examples manifest (folder, label, start definition,
page or not) read by both would make the examples data, like everything
else.

main.ts is 4,365 lines with the state of a gesture in module variables
(`swapped`, `wrapping`, `openBefore`, `deleted`) that undo reads by
position (`undo.length === swapped.at`). It works, and E193 just fixed one
of its cases; the next "two edits that are one undo step" will be harder.
Not a row of its own beyond E205's manifest; worth knowing before adding a
fifth such variable.

## 10. NODE-EDITOR.md's audit is stale (E206)

"Same edits in both views (audit, 2026-10-24, BACKLOG E97)" lists the
gestures and checks each in Blocks and Graph. Added since and missing:
Wrap in…, Turn around, a list's sockets (E166), a function's result
ports (L128), Group into a function, Implement, Answered later. Either recheck and extend the table, or drop the claim that
it lists every gesture.

## 11. Saved inputs are traced with no time limit (E207, by reading)

`boundedTrace` (main.ts) limits the wires' values to 200 ms, except when
the definition has saved inputs (`doc.examples`) or no inputs: then
`trace` runs on the page's own thread to the end ("Values you gave run to
the end"). A function that loops on its saved inputs, or a value
definition that takes minutes, would hold the page on every redraw of
that definition with no Stop. Not reproduced here; worth a test with a
looping definition before deciding the fix (a longer limit with a message,
or the run in the worker as Run main does).

## Not findings

- No page error in any probe; the redraw's own error screen (render's
  catch) was never reached.
- The phone layout fits (scroll width = window width at 412 px).
- Long press opens the menu in both panes; QA covers it daily.
