## 1. Float64 overflow on three engines

[FLOAT-VALUES-2026-11-01.md](../../design/numbers/FLOAT-VALUES-2026-11-01.md)
§2 splits a float's failures into two kinds. *No answer* (`x / 0`,
`sqrt(−1)`) is a `Choice`, checked on the argument, and the engines agree
on it (compiler/test/finite.test.ts). *Too big to hold* is "not in the
type: an abort, like running out of memory", and "can be checked late",
because "pure code can't observe the difference between 'failed at the
multiply' and 'failed at the compare after it'", as with Haskell's
imprecise exceptions.

That last sentence doesn't hold here. Haskell can only catch an imprecise
exception in IO. In Ters a handler of Abort is an ordinary `match` in pure
code, and L125c1 makes the overflow stop "an Abort performed where the
operation was … so a handler of Abort in the program gets them". So the
handler sees where the check happens. A probe, with `a = b = 1e300`:

| definition | evaluator | compiled JS |
|---|---|---|
| `caught(a, b) = show(match a · b { abort(why) → 0 })` | `0` | stops: "the answer is too big for a Float64 (overflow)" |
| `unused(a, b) = show(length([a · b]))` | stops: overflow | `1` |
| `dropped(a, b) = let x = a · b in show(a)` | stops: overflow | `1e+300` |

In `caught`, the evaluator's multiply performs the Abort inside the
handler, which answers 0. Compiled, the multiply gives ∞, the ∞ leaves the
handler as its answer, and `show` stops the program outside, where nothing
handles it. On WebAssembly and C a stop "ends the program rather than
being an Abort a handler in the program gets" (FLOAT-VALUES, L125c2), so
they stop too, for a different reason. Shaders keep no checks, so on the
GPU the same function gives ∞ or NaN.

`unused` and `dropped` are the rule's other half: "an overflow nobody uses
may not be reported". The evaluator reports it anyway. That's allowed, but
it means "evaluated and compiled say the same" (I111, LANGUAGE.md) holds
only for programs that don't overflow, and nothing says so.

**Why it matters.** The README lists "Targets don't bend the language"
as a goal whose rule holds. Here one well-typed definition gives three
answers on three engines. The Clifford demos normalise vectors whose
weight can be tiny, so an overflow in a handler isn't far-fetched, and
the editor's preview swaps from the evaluator to compiled code a few
seconds after opening (R4 §5), so the user can watch the answer change.

**Fix, smallest first.** Make overflow what the design's own table says
it is: "not in the type: like running out of memory". That means a stop no
handler in the program can catch, on every engine. The evaluator and
compiled JS stop performing it as `Abort`, and WebAssembly and C already
behave that way. Then checking late is sound, because the only observer
is the end of the run. "An overflow nobody uses may not be reported"
stays, and LANGUAGE.md's error table says that the engines agree up to
it. The other fix, checking at every handler's exit in compiled code,
keeps overflow catchable but adds a check per handler on every target,
and shaders still can't do it. Todo test: compiler R7 §1.

## 2. The pace, and what checks it

The project rule since 2026-10-22 is step by step: one change per PR,
bugs before features, check after each merge. Each PR this week keeps the
first two. The third is under strain:

- **Check main finished 10 of its last 60 runs.** All 10 were green, and
  48 were cancelled while queued (a newer merge replaces the waiting run;
  each run tests everything since the last green, so nothing is skipped).
  But a run that finishes once an hour on a day with 40 merges points a
  failure at forty candidates, and R4 found the run is about 19 of its 20
  allowed minutes. I110 has been in the Inbox since R4 without a lane.
- **Reviews overlap.** R4, R5, R6 and this one were written within 36
  hours: two from the weekly routine, two the coordinator asked for to
  refill lanes. Each is good, but the weekly whole-project review now
  mostly restates the others' status tables. Suggestion: keep the weekly
  routine for cross-cutting questions (engines, goals, size, process),
  and let lane reviews own their findings. If a lane review ran in the
  last two days, the weekly one can say "see R6" and go straight to what
  nobody looked at, as this one tries to.
- **BACKLOG.md's "Next up" table is unreadable.** The Language row is one
  cell of about 3,000 characters listing 50 finished PRs. DONE.md already
  keeps the history. "Next up" should name the next three items and
  nothing else.

Growth by itself isn't a finding. The goal "one uniform system" is, and
the risk is the one R4 §7 named: one meaning written once per engine. §1
is an example. Finite `Float64` was designed once, then built five times
(L125a evaluator, L125c1 JS, L125c2 WASM and C, the shader exemption), and
the five came out with three different semantics for one case. The I111
agreement test catches differences on the examples. It can't catch a
difference that no example exercises, and that's the case in §1. A
generated differential test would: small random typed programs from the
palette's own fillings, run on every engine. It is the next step after
I111 and worth its own row.

**On course?** Yes. The language work this week (finite floats, tuples, one
`<`, Int counts) went at the core, not just at targets, which is what R3 and
the language review asked for. The thing to protect now is the claim that
the engines mean the same thing. It's the claim the targets most often
test, and it's now checked only on the examples.
