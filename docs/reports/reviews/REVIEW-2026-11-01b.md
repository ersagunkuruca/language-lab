# Fifth review: tuples, the hash tables, tree lists and the simulated world

Written 2026-11-01 (late evening UTC) at `9585935` (after PR #961), a
critical review of what landed on 1 November, asked for by the
coordinator during Ersagun's "as many tasks as you can" run. It follows
[REVIEW-2026-11-01.md](REVIEW-2026-11-01.md) (R4, the same morning) and
works the same way: the new code and its docs were read, the suites were
run, and the holes below were found by trying to break things with small
probe programs written with the DSL. Nothing is fixed in this PR and no
code is touched: each finding has a repro here and a row in BACKLOG.md
(Language lane L137 to L144, Compiler lane C74 to C77), ranked bugs first.

**What was looked at:** L128a to L128e (tuples, `f(p)`, named result
ports), C71 and C72 (every version of a hash table a value, sorted entries
kept), C45 (`tree of List`), C70, L63 (`simulated(seed, action)`), L43c
(blade masks from callers, in staging and shaders), C40 (a compiled main
that waits), L133 to L136 (text tests, take and drop, one sum). The list
sockets (E166) are the Editor lane's and were only read for the language
question they leave open (E166b).

**What was run:** the projectional suite, a sweep of every example's
`main` through `lab run` and through `lab compile` then node, a random
test of the hash table's versions against a reference map, and the probes
quoted in each section.

## The verdict, first

The day's work is solid where it was tested hardest. The hash table's
"every version stays a value" (Baker's shallow binding) survived 300 random
histories of 60 steps each, reading old versions in between, with no
mismatch against a plain map. The examples that print give the same
output evaluated and compiled. Masks from callers are conservative in
every case I could build: a definition used as a value, called from a
lambda handed on, or called where the reading can't follow gets every
part.

The weak spots are the edges between new features and old ones:

1. **"Every function takes one value" holds only at a call whose callee
   is known.** `f(p)` works for `times(p)`, but `apply(f, p) = f(p)` given
   `times` is refused, and so is anything that hands a two-input function
   to a higher-order one with tuples. PORTS-2026-11-01.md promises the two
   are "the same thing"; in the types they are still two. §1.
2. **The simulated world simulates only Await.** `now` reads the real
   clock and `wait` really sleeps inside `simulated`, so a program that
   reads the time gets different answers from the same seed, and a 5 s
   virtual timer is seen by `now` as 0.3 s. §2.
3. **`tree of List`'s fold is about 100 times slower than walking the
   items**, because it rebuilds each arm's rest as a tree even when the
   arm never names it. A `sum` over a list the chooser stored as a tree
   pays n log n plus an allocation per item per level. §4.

## 1. Tuples: one value in, but only at a known callee

L128a's checker rule (infer.ts, "One value given for several inputs") fires
when the callee's type is already a function of 2 to 8 inputs and the
call gives one argument. It unifies that argument with the tuple of the
inputs and marks the call; spread.ts then gives the call its parts. Where
the callee's type is not known yet, the rule doesn't fire, and the call is
typed as a call of one input.

**Repro** (probe with the DSL, checked with `checkOptions`):

```
times(a, b) = a · b
apply(f, p) = f(p)                 -- apply : ((a) -> b, a) -> b
use apply(x) = apply(times, tuple(x, x))
  error: apply needs (a) -> b here, got (a, a) -> a
pair spread(x) = times(pair(x, x))
  error: times takes 2 inputs: given one, it needs (a, a) here, got Pair a a
```

So `(a, a) -> a` and `((a, a)) -> a` are still two types. Every
higher-order use hits this: `map(times, list of tuples)`, `each`, `keep`
with a two-input test, a function value passed through a record, and the
editor's wire from a tuple-giving node into a function-valued port. It is
also order dependent: the same call checks or not depending on whether the
callee's type was settled before the call was reached.

**Fix.** Make it a rule of unification, not of calls: a function type of
n ≥ 2 inputs unifies with a function type of one input when that input
unifies with the n-tuple (ML's view, which PORTS §1 cites). spread.ts
already turns the call into an ordinary one afterwards; a function value
used at the other shape needs a small wrapper made where the types meet,
(p ↦ f(p.first, p.second)) or ((x, y) ↦ f(tuple(x, y))), which the
checker can record as it does `spread`. Add the four probes above as
tests. Row **L137**, P1.

## 2. The simulated world simulates only Await

`simulated(seed, action)` (prelude-source.ts `simulated world`) handles
`await` and `start timer` on a virtual clock and seeds Random. Its type
shows what it leaves out:

```
simulated :: (Float64, () -[Abort, Await, Random, e]-> a) -[Abort, e]-> a
```

Time and Wait are in `e`, so they reach the real world.

**Repro:**

```
simulated(1, () =>
  before = now()
  t = start timer(5000); await(t)    -- virtual: takes no time
  wait(300)                          -- real: sleeps 300 ms
  now() − before)
→ 308   (real ms 390)
```

The virtual clock moved 5,000 ms, `now` saw 308, and the run really slept.
Run it twice and the answer differs, which defeats "the same seed gives
the same schedule every run" for any action that reads the time: a
timeout written as `now() − started > limit`, a rate limiter, a log line
with a time in it. FoundationDB's simulation (the prior art the doc cites)
virtualises time for exactly this reason.

**Fix.** `simulated world` handles `now` (the clock it already passes
along) and `wait(ms)` (advance the clock, no real wait). Tests: the repro
above gives 5300 every run; two runs of one seed print the same `now`s.
Row **L138**, P1.

**Smaller, same handler.** The schedule's tie-breaks and the action's own
random numbers come from one seeded stream. An action that draws one more
random number moves every later tie-break, so a seed found to reproduce a
bad interleaving stops reproducing it after an unrelated edit. Two streams
split from the seed (the scheduler's and the action's) keep a seed
meaning one schedule. Row **L142**, P3.

## 3. Two 2-tuples: `Pair` and `Tuple2`

std's `Pair a b` (fields `fst`, `snd`) predates L128 and is what `entries
of`, `zip`-like library code and many examples give. `Tuple2 a b` (fields
`first`, `second`) is L128's. They are different types, so a map's entries
can't be given to a two-input function with `f(p)` (§1's second error),
and a program that mixes them converts by hand. "Two tuples of the same
types are one type wherever they come from" (std.ts) is true of two
`Tuple2`s, not of a `Pair` and a `Tuple2`.

**Fix.** One type: `Pair` becomes `Tuple2` (its constructor `pair` a
name for `tuple` at two, `fst`/`snd` read as `first`/`second`), with the
saved-file upgrade that `upgrade.test` already does for renamed
definitions. Check the examples and the library's maps after. Row
**L139**, P2.

## 4. `tree of List`: the fold rebuilds every rest

`list tree fold` (list-tree.ts) turns the tree into its items and folds
them from the back, building each arm's rest as a tree again with one
`cons` (log n) per item, because a fold's arm may name its rest. Most
folds don't (`sum`, `length` as written, `each`, `map`'s own fold), and
then the tree built is thrown away.

**Repro** (the evaluator, TREES' own definitions, summing):

| n | `list tree fold` | `items of list tree` |
|---|---|---|
| 1,000 | 200 ms | 2.2 ms |
| 8,000 | 1,770 ms | 17.5 ms |

The cost table says the fold is linearithmic, so the chooser is not
misled; but every program the chooser stores as a tree pays it on every
fold. The fix is the one GAPS.md M3 made for the Map and Set trees' heads:
a fold whose arms never name the rest walks the items in order (n), and
only one that names it rebuilds. The row then lists two fold costs, which
the chooser can tell apart the way it does `heads`. Row **C75**, P2.

**Smaller, same file.** The boundary's way back from a builtin's list
(`stored list`, library-reps.ts `listBoundary`) folds the list with the
tree's `cons`: n log n and a rebalance per item. A balanced tree can be
built from a list of known length in n steps (split at the middle). Row
**C76**, P3.

## 5. Positions are Float64, lengths are Int

```
take :: (List a, Float64) -> List a
drop :: (List a, Float64) -> List a
item at :: (List a, Float64, a) -> a
replace at :: (List a, Float64, a) -> List a
length :: (List a) -> Int

first half(xs) = take(xs, length(xs))
  error: take needs Float64 here, got Int
```

L135 counts like `item at` (rounding to the nearest, half up), which kept
them consistent with each other but not with `length`, `list tree size`
(Int), or Array's `item at` (Int). Every loop that counts items and then
takes that many converts. Since L136 the library has one `sum` for every
number type; positions and counts should be Int, the way `length` and
Array already are, with the rounding Float64 versions dropped (or kept
generic over number types if a reason turns up). The tree representation
then loses its `floor(p + 0.5)` (list-tree.ts `position`). Row **L140**,
P2, with the saved-file upgrade for the examples that pass Float64s.

## 6. An `any of` inside an `any of`

The world's Await (run.ts `unhandled`, and runtime.js `goOn` since C40)
aborts with "any of a ticket that is itself an any of can't be awaited
yet". The probe waited the full 5 s timer before it reached the nested
ticket and aborted. `simulated` answers the same ticket (its `ready at`
recurses through `first ready`). So the same program works under test and
fails in the world. Its `which` function composes: the outer `which` of
the inner one's index. Row **L141**, P2: both worlds handle nesting, one
test run under the world and under `simulated`.

**Same code, written twice.** The world's answer to Await is in run.ts and
again in runtime.js; the two match today line for line, and §6's fix has
to be made in both. runtime.js keeps `timers` at module level while the
evaluator keeps them per run, so in the editor's worker a ticket number
from an earlier compiled run is still "from this world" in the next one.
Row **C74**, P3: one world module both use (or a test that runs the same
waits through both), timers per run.

## 7. Blade masks stop at records and tuples

valueMasks (grades.ts) reads each definition with its callers' masks. When
a callee gives anything but a multivector, `onCall` returns `top`, which
becomes "every part" for whatever is taken out of it. Bounce's and
Spacetime's states are records of multivectors, and since L128 a function
giving two multivectors gives a tuple, so the precision is lost exactly
where programs are heading. Not a correctness problem (wider is safe), a
staging gap: the reader needs a record value whose fields are masks, as it
already has for lists (`{ k: "list", item }`). Row **C77**, P3, measured on
Bounce's step first (if staged code doesn't shrink, close it).

A note for whoever touches it next: masks are only right because every
definition called from outside is in `open`. Today `lab compile`, `lab
render`, `build-web`, the editor's worker and `lowerScalar`'s roots all
pass their entry points, and definitions nobody reaches aren't compiled
(C67a). A new caller that compiles a definition without naming it as an
export would get masks of 0, that is, inputs staged as zeros, silently. A
one-line guard (a definition compiled but not reached from `open` gets
every part) would make that impossible. Folded into C77.

## 8. Smaller things

- **A tuple's text.** `show(tuple(1, "a"))` is `tuple(1, "a")`; its type
  is shown `(Int, Text)` and the design writes values `(1, "a")`. Row
  **L143**, P3 (show, and the text view's literal, together).
- **`recheck` drops what a run needs.** signatures.ts `fill` copies types,
  holes and errors from the earlier check for definitions not checked
  again, but not `spread`, `answered`, `opAt` or `implementations`. A
  program run from that info would call a two-input function with one
  tuple. Only modules.test.ts calls `recheck` today. Row **L144**, P3:
  copy them, or delete `recheck` if the palette's own path replaced it.
- **The hash table under alternating reads.** Correct (the random test
  above), and each put on the newest version is constant. Reading two
  versions in turn costs the distance between them each time, which the
  design note says. No row: nothing in the examples does it.
- **Commit messages.** The lanes' squash merges carry every commit message
  of their long-lived branch: #952's message lists C52, C30, C40 steps 1
  to 2d, C30b, C65, C66a to C66c3, I79 … before its own. `git log` and
  `git blame` no longer say what a commit did. Each squash should use the
  PR's own title and summary only. Row **P4**, for the coordinator.
