## The verdict, first

What was built today holds where it was measured. Every example with a
`main` compiles and runs; R11's crashed `backwards` stays fixed. All 72
saved program files print back byte for byte. A page's log is now
bounded: bounce's stays at about 1.2 KB a simulated second within its
window, and the heap after a collection stays flat (141, 138, 134 MB at
10, 20, 30 s).

What isn't working is **how a merge is checked**:

1. **Main was red for two hours, through eight merges, and the merging
   lane didn't notice.** L244 (#2581) changed negate to read off a sum,
   so negate of 0 gave +0 rather than −0. A PR runs only the typecheck,
   so the PR went in green. Check main failed 15 minutes later, at
   11:58. About seven more merges then landed on a red main, each Check main
   red, until the Nightly at 12:53 surfaced it and the Compiler lane
   passed it on at 13:47. Fixed in #2592. The rule "check Check main
   after each merge" (WORKFLOW.md) was not followed by the lane that
   merged, and nothing else tells anyone. §1.
2. **Stepping back on a page that hears frames costs seconds a step.**
   The window keeps a snapshot every 10 seconds. A step replays from the
   snapshot before it, through every frame since. On bounce, interpreted
   in Node at about 1.6 s per simulated second, one step takes 7 to 12
   seconds. The page panel's Back steps one event at a time, so stepping
   back through a few frames of an animation is unusable. §2.
3. **The compiled handover loses cells in the browser, not in Node.** In
   the editor, after Pause, a step and "Go on from here", the compiled
   page shows Rolls: 0. The same sequence in Node shows Rolls: 1. Nothing
   tests the editor's swap with the site's prebuilt page, so the two can
   drift apart unseen. §3.

## 1. What a merge is checked by

A PR runs one check, the typecheck, which takes 30 seconds. Before
merging, a lane runs the test files that it thinks cover the change, by
name (run-affected-before-merge, #1745). After the merge, Check main runs
every test file the change reaches, in six shares, in 15 to 20 minutes.
The Nightly runs everything.

L244 changed invertible/src/expr.js. `node ters/test/affected.ts` maps
that file to arith.test.ts, and Check main ran it and failed. The lane
ran its own choice of files instead (one-sum.test, atoms.test). It has happened
before: #932 on 11-01 broke the site for 13 merges the same way, which is
where the rule to read Check main after a merge came from.

The cost of the gap is not the bug. Once it was found, the bug took five
minutes to fix. The cost is that **about eight merges landed on a red main**.
Each of their Check mains was red for a reason that wasn't theirs, so
none of them could tell whether they broke something too. One of them
did: audio.test's calculus check went red in the same window, and the
Compiler lane traced it to its own change only once the Nightly listed
both. The first red hid the second.

What could close it, cheapest first:
- **The merging lane reads its Check main.** It is already a rule. It is
  also the rule most often skipped, because a lane has moved on by the
  time Check main finishes 15 to 20 minutes later.
- **Before merging, a lane runs `node ters/test/affected.ts origin/main
  --list` and runs every listed file whose name relates to what it
  changed,** not a set it picks by memory. affected.ts already knows the
  map from files to tests.
- **The coordinator watches Check main** (it already sees every merge),
  and tells the lane whose merge first turned it red. A red that lasts
  more than one merge is then never anyone's but that lane's.

Running affected tests on every PR in CI would close it fully, but the
Actions budget ($20 a month across the account) is why PRs run
only the typecheck. I don't recommend it without Ersagun's word.

## 2. A step back on a page that hears frames

The window (WORLD-LOG-WINDOW.md §2, §3) keeps a snapshot every 10 seconds
of events. A step to event n restores the snapshot before it and gives
every event since again. That is the right shape: rr and Redux DevTools
do the same. But the distance between snapshots is counted in seconds,
and a page that hears `frame` has 600 events in 10 seconds.

Measured on bounce, interpreted in Node with the editor's window, after
35 simulated seconds (2,100 frames):

| step | time |
|---|---|
| to(2099), one back from the end | 7.4 s |
| to(1050), the middle | 11.6 s |
| to(1), just after a snapshot | 9 ms |
| to(2100), the end again | 7.8 s |

The interpreter runs bounce at about 0.6 times real time (16 s for 10
simulated seconds). So the cost of a step is up to the replay of a whole
segment. The editor's Back button costs that on every press.

What would fix it, by cost:
- **Snapshot by events as well as seconds**: every 10 s or every 60
  events, whichever comes first. A snapshot costs one map entry per cell
  (values are shared), so 10 times as many snapshots in the window is a
  few hundred entries more. A step then replays at most 60 events, about
  0.5 s on bounce.
- **Keep the snapshot a step lands on.** Stepping back one at a time then
  replays from the step before rather than from the segment's start. This
  is rr's "checkpoint as you go".

The first is a one-line change and the measure that matters. The second
can wait until the first proves too coarse.

## 3. The handover to the compiled page

The Editor lane traced it in the browser on main at 332f930, with the
site's prebuilt dice:
1. compiled, four Rolls
2. Pause
3. `to(0)`, then `to(1)`, which shows Rolls: 1
4. `resume()`
5. `mountCorePage(…, { handFrom })`

The compiled page then shows Rolls: 0.

The same sequence in Node shows Rolls: 1, compiled with
editor/pageCompile.ts `compilePageProgram` (the function prebuild.ts
uses), and handOver moves the counts. Cell 0's values look the same on
both sides: the interpreter's is a cons list of numbers, and the compiled
first is a cons class with `tag` on its prototype and f0/f1.

The cause isn't known yet. #2597 makes mountCorePage return how many
cells it moved, so the editor can see whether this is "nothing moved" or
"moved but not shown".

The finding is the gap, not the bug: **no test runs the editor's swap
with the prebuilt page.** page.test.ts mounts a compiled page the way
the editor does, but in Node, from a program compiled in the test. The
startup handover (interpreted, then compiled a few seconds later) has
the same gap. A click lost there would go unseen too.

## 4. The design note's example

WORLD-LOG-WINDOW.md opens with tumble's hour: about 216,000 frame
entries, about 40 MB. Tumble animates with CSS (`animationend`) and never
hears `frame`. Its log grows only with taps. The pages that hear `frame`
are agent, bounce and spacetime. Measured on bounce, before the window
(I239a), a frame cost about 20 bytes as JSON. The note's design is right,
but its numbers are a guess written as a measurement.

## 5. The Nightly

All six Nightly runs that finished today finished red. Since I208 it runs in parallel
and finishes in about 20 minutes, where R11 found it cancelled every
night. That is the progress. Each run found new reds from the day's
merges: I240's printer, L244, I245, the editor smoke. Each lane fixed
them within hours. I219 tracks them. The Nightly is now doing the job
Check main should do (§1): it is where a red is first read.

## What is good

- **Every example compiles and runs.** All 52 examples with a `main`
  compile with `ters compile` and load and run with no error. That
  includes `backwards`, which crashed on load at R11.
- **The saved format is exact.** All 72 program files print back byte
  for byte. Their nodes compare equal through `sameValue`, never JSON
  text, and `ters diff` and `ters merge` read either spelling.
- **The library rebuilds to itself.** `node library/build.ts --check`
  passes since I244. The case tables no longer depend on the host's
  Unicode.
- **The world log is bounded.** Its memory no longer grows with the run.
  Stepping and going on work on the interpreted page and, since I239f,
  after the compiled page has taken over.
