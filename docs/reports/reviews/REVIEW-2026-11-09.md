## 2. The whole library is type-checked for every program

A probe (`R10 §2`): a fresh `Lang` over the library, a `main` that prints
`"hi"`, then `infer`:

```
tiny main infer ms 2567   typed nodes 40021 of 43568
tiny main infer ms 18     (second call in the same process: cached)
```

A CPU profile of `lab run examples/wc` (empty input) puts 1.9 s of its
3.3 s of samples in `infer`, most of the rest in loading modules and
TypeScript stripping. The compiled program it produces runs in 0.15 s.

| | time |
|---|---|
| `lab check examples/wc` | 6.5 s |
| `lab run examples/wc` (compiles through the core IR) | 4.5 s |
| `lab run --evaluator examples/wc` | 4.7 s |
| `lab compile examples/wc` | 4.5 s |
| the compiled `wc.js` | 0.15 s |
| loading `LIBRARY` alone | 0.5 s |

Why it happened: the library grew to 43,568 nodes. The cases module's
Unicode tables (L214e) are about 10,000 nodes, and `ters/library` holds
13 MB of JSON (`cases.json` 3.9 MB, `prelude.json` 3.4 MB, `steady.json`
1.7 MB, `numbers.json` 1.4 MB, `collation.json` 1.2 MB, `trees.json`
1.1 MB). `library.ts` imports `cases.json` unconditionally. No test or
budget watches start-up time, so nobody saw it pass a second.
BLIND-SPOTS-2026-11-03 #7 ("performance that changes silently") named
this class a week ago.

Why it matters: it's the first thing an outside user meets (`lab run` on a
ten-line program takes four seconds), it's paid by each of 125 test files
in every Check main run (about 5 minutes of a 20-minute budget, §3), and
the MCP and editor sessions pay it when they start.

**Fix.** The library's definitions are pinned: their types are known by
hash (signatures.ts). `infer` should type a program's own definitions and
take the library's types from their pins, typing a library body only when
something asks for it (the palette, a backwards run that reads it). Then
the Unicode tables load only when a program calls `collate`, `uppercase`
or `graphemes` on a target without a host. A start-up budget in the suite
(`lab check` of `wc` under 1 s) keeps it there. Todo test R10 §2 counts
typed nodes rather than time, so it isn't flaky.

## 3. Check main

The last 40 Check main runs: 38 cancelled while queued, 2 running at the
time of reading (on today's merges). GitHub's API failed when asked for
older pages, so how long it has been since a completed run wasn't
measured. R4 raised this as I110 on 11-01 and R8 again on 11-02. I110
isn't in BACKLOG.md or DONE.md now: it was dropped without being closed.

Each run tests everything since the last green one, so nothing is skipped
for good, but on a day of 390 merges (11-05) a failure lands on hundreds
of candidates. §2 is part of the cause: 125 test files at 2.5 s of
library typing each.

**Fix.** §2 first, then measure Check main again. Put I110 back as a row
(or close it with a reason in DONE.md).

## 5. The reference engine is too slow to be the reference

The evaluator defines what a program means: every other engine is checked
against it (I111's examples, C101's generated programs). Two gallery
examples are left out of the core-IR agreement test
(`compiler/test/core-js.test.ts`, `skip`): `numbers`, because the evaluator
runs out of memory counting in Peano `Nat`, and `agent`, whose A* search
takes the evaluator minutes (added 11-06). As examples grow toward real
programs, more of them will drop out of the one check that says the
engines agree. L118c (closure compilation, "likely 3 to 10×") is the row
that would bring them back, and it is held.

up. Until they are, "serious language for mobile" is a goal nobody is
working on.
