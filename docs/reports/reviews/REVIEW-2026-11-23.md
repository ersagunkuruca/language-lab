## 1. Main red for four days (high)

```
Check main, newest first (G green, R failed, C cancelled, ? running), 200 runs,
11-23 00:03 back to 11-18 18:54 UTC:
?RRRRRCRCRRRCRRGCCCRCRGRGCGRGRCCGRCRRCCCCCCCCRCCCCCCCCCRRCCCCCCRRC

```

The week merged 319 PRs. Most of them landed on red.

**Why it looks intermittent.** Check main runs only the tests that a
line changed since its own last run reaches (`--since-map`, T16). So a
test that is broken shows up again only when a later push touches what
it covers. The history alternates R and G, and each lane that "looks at
Check main for your commit" usually sees a run that names no commit of
its own. When a test fails for a reason the bisect can't pin, the
summary says `no one commit to blame (it may be flaky)`, and nobody owns
it. The rule asks every lane to stop, but nothing makes any lane stop.

**What was failing at the end** (run 45085846778, on `ce9d69f`), three
files:

- `ters/test/reference.test.ts`. Since G9b (#3109, 11-22 22:26 UTC),
  std's Mesh, Placed, Target, Draw, Pass, Frame and `draw` were offered
  to programs with no note and no section in library/reference.ts.
  **Fixed in #3123** (notes, a Frames section, LIBRARY.md regenerated).
- `ters/test/units-in-types.test.ts`. Also since #3109: std's Placed has
  a `position` field, so `b.position + 1.5 m` on an input nothing
  settles read "as a Body or as a Placed", and the MCP refused it. Games
  and physics name a field `position` all the time, so every such
  program hit it. **Fixed in #3124**: with no `as` and no other field
  read to settle it, the MCP takes the one reading whose types are all
  the program's own (session.ts `programsOwn`). Two of the program's own
  still ask (E186). The editor still offers both readings as choices.
- `compiler/test/branches.test.ts`, "a map's items cross with what its
  function captured" (C42), says `branches on workers: 0`. It passes
  alone here, twice. The test asserts that some of 12 items ran on a
  worker. branches-rt.ts starts the pool only after the main thread has
  done `WORTH` ms of a site, and the main thread claims items from the
  end while the workers start. On a loaded runner, the main thread can
  finish all 12 before a worker is up. This is a timing assertion about
  an adaptive scheduler, not a wrong answer. **Not fixed here.**

Earlier in the week, two of the reds were Check main itself hanging, and
each was fixed by a row: I345 (#3070, a recorded test file stopped after
8 minutes) and I347 (#3081, a walk down an empty text's characters never
ended). The failed runs from 11-18 to 11-21 were not read file by file:
this container can't fetch whole run logs.

**Fix:**

1. **Make P10 mechanical.** A PR's checks fail while Check main's last
   finished run on main has been red for more than an hour, unless the
   PR names a failing file in its title (a lane's own fix merges, as P10
   says). A rule every lane must remember failed twice in two weeks. A
   red check needs no one to remember it.
2. **Carry failures forward.** Check main runs again every file that
   failed in its previous run, whatever the push touched, so a red file
   stays red in every run until it passes. Then the history says
   "broken" and not "flaky".
3. **branches.test's C42 assertions** wait until the pool is up, or
   assert only when the run lasted longer than a worker's start (as
   `slowStart` already does without esbuild). This is a row for the
   Compiler lane.

## 2. Std's names reach into programs (medium)

The units-in-types failure (§1) is one case of something broader. A
type added to std brings its field names into every program's field
readings. Placed's `position` is the one that broke a test.

Event (`x`, `y`, `value`, `key`, `seconds`) and Request (`url`, `body`,
`method`) were already there. Any program whose own type has a field `x`
or `body`, read on an input nothing settles, gets the same "reads as A
or as B" from the editor's typed fill. #3124 settles it for the MCP. In
the editor, the person picks a reading, and that is by design (E186).

Probe: a program that defines its own `Mesh` (a points field), its own
`Frame` (number and seconds) and its own `draw`, and calls them. It
checks and runs (`2`, exit 0). Std's type names don't clash with a
program's, only their field names do.

Stage 2 adds more std types (G10 textures, G11 meshes from files), each
with fields like `width`, `height`, `name`, `position` and `colour`, so
this will come up again. The reference test caught #3109 only because it
also checks notes. No test reads a program with a field std also has.

**Fix:** a row (Language lane) to settle the rule in the checker, not
only in the MCP. When a field read on an unsettled value is the
program's own and also a library type's, and nothing else decides, the
program's own is meant. A test should cover each std type's field names
against a program that has a field of each name.

## 3. A choice goes stale when its words change (low)

`examples/flock-page.choices` is the only choices file kept in the repo
(L280a). `ters check examples/flock-page` reports 5 stale entries and 9
new ones today:

- **9 new:** the C target's places and threads (L280h), which came
  after the file was written. Expected.
- **5 stale:**
  - 4 schedules whose pick is the same, about the same id, where only
    the words for the job changed ("flock over over flat map's flock
    over walk" is now "flown's flock over walk").
  - 1 place that gained "in 32 runs".

`staleChoices` (cli/choices.ts) compares whole lines, so rewording the
part meant for a person makes an entry stale. A held entry is spared
(`heldIn`), but an unheld one isn't. Nothing tests the kept file
against today's compiler.

**Todo test R12 §3:** an entry with the same id, pick, choices and
target, but different words, is not stale.

**Fix:** stale compares the id, the kind, the pick, what it is among and
the target, not the words. Add the kept file to a test that runs
`ters check` on it.

## Is it still on course?

On course for programs on every target (the 11-22 example sweep found
one gap, wav-file's bytes, fixed in #3121 and #3122), for compile
speed (R11 §2), and for stage 2 of the game work. The risk is the one
R11 named, and the answer it got was a rule. The project has a safety
net, Check main, built to be cheap, and it works when someone acts on
it. For four days nobody did. The fix has to be something that stops a
merge by itself (§1).

## Recommended order of fixes

1. **P10 made mechanical, and failures carried forward** (§1). This is
   CI work for the coordinator to assign.
2. **branches.test's C42 assertions** without the race (§1). Compiler
   lane.
3. **A program's own field over a library type's, in the checker**,
   with a test across std's field names (§2). Language lane.
4. **Stale by meaning, not words** (§3, R12 §3).
