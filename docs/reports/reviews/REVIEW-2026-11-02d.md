# Ninth review: the language as machine and board use it

Written 2026-11-02 after PR #1123, at the coordinator's request (after
L166, before L150b), by the Language lane. It reads the two biggest
programs written in the editor, `compiler/gaps/machine` (round 9: an
assembler, checker, optimizer and interpreter, 112 definitions) and
`compiler/gaps/board` (round 8: a kanban page, 112 definitions), and asks
one question of each place where they're long, repetitive or roundabout:
is that the program, the library, or the language?

**How it was read:** every definition was printed with the MCP session's
`view` (`ters/mcp/session.ts`), and each suspected gap was tried with its
`eval` against the program. Nothing is fixed here. The rows are at the end.

## The verdict, first

Both programs read well, and most of their length is honest: an
interpreter of 21 instructions has 21 arms. Three things in the language
make them longer than they should be, and they recur in both:

1. **Changing a record means writing all of it again.** machine builds
   its 8-field `Machine` from scratch 12 times to change one or two fields
   (`go on`, `set register`, `pushed`, `popped`, `called`, …), and its
   5-field `Options` 6 times. board does the same with `Quick` and `State`.
   `set(field, record, value)` exists (LANGUAGE.md "Updating a record"),
   but changes one field, so two fields are two nested `set`s, and the
   programs don't use it. §1.
2. **A field that several cases share can only be reached by a match.**
   machine's `to` is in six of `Instr`'s cases, and four definitions
   (`targets`, `threaded`, `moved`, `next places`) are six-arm matches that
   each read or replace it. board's `timer id` and `running id` are the
   same for `Timer`'s `id`. §2.
3. **Choosing by a literal value is an if-chain.** machine's
   `instruction of` is 21 nested `if op = "…"`, and `options of`, board's
   `stage from key` and `on key` are the same shape. `case of` (L164b)
   now says it as a list of pairs, and the literal-arm match (L164c) is
   the real fix. This review only adds evidence to L164c. §3.

The rest is library gaps (§4) and places where the programs could now use
what the library has gained since they were written (§5). Two things that
looked like language gaps are the text reader's (§6).

## 1. Changing several fields of a record

```
‹go on›(machine) = machine(machine.pc + 1, machine.registers, machine.memory,
                           machine.stack, machine.steps, machine.printed,
                           machine.running, machine.counts)
```

That's a one-field change written as eight. With `set` it is
`set((m) ↦ m.pc, machine, machine.pc + 1)`, and the evaluator does it
(`set((c) => c.points, card(…), 5)` gives the card with 5 points). But
`set register` changes `pc` and `registers`, and `stepped` changes `steps`
and `counts`, and there `set` nests: `set((m) ↦ m.pc, set((m) ↦
m.registers, machine, r), machine.pc + 1)`.

**Proposal (L167):** `set` takes a tuple of fields as its path, and a
tuple of values: `set((m) ↦ (m.pc, m.registers), machine, (machine.pc +
1, r))`. No new construct: a path is already a function the checker
reads, and tuples of ports are already values (L128). The checker accepts
a tuple of fields or field paths, each written in place and no two the
same or one inside another, so the update still has exactly one answer.
Today `eval` refuses it ("expected a value at 1": the reader doesn't take
a tuple in a lambda body yet, and the checker wouldn't take the path).
The prior art is OCaml's and Elm's `{ r with a = …; b = … }`, and
Haskell's record update syntax, which update several fields at once.

That the programs don't use the one-field `set` either is partly the
editor's to answer: whether the palette offers `set` when a record of the
same type is being built from another's fields. That question goes to the
Editor lane as E211.

## 2. A field several cases share

```
targets(code) = flatten(map(code, (instruction) =>
  match instruction
    jump(to) → [‹target of›(to)]
    jz(a, to) → [‹target of›(to)]
    jnz(a, to) → [‹target of›(to)]
    jlt(a, b, to) → [‹target of›(to)]
    jeq(a, b, to) → [‹target of›(to)]
    call(to) → [‹target of›(to)]
    otherwise → nil))
```

`threaded` and `moved` are the same match with `to` replaced, and `next
places` again. `jump(number(3)).to` is refused: "to belongs to one case of
…; use a match to reach it" (infer.ts). The language's own answer to "the
value inside, or nothing" is Choice (LANGUAGE.md "Pattern matching by
choice"), and that answer fits here:

**Proposal (L168, design first):** reading a field on a type with several
cases is allowed when the field is one that several cases declare (same
name, same type). It has no answer (Choice) on a case without it, and
none of that when every case has it. `set` through such a field changes it
in the case that has it and has no answer otherwise. Then `targets` is
`flat map(code, (i) ↦ first([‹target of›(i.to)], else nil))` and
board's `timer id` is `tm.id`.

The open question is what "the same field" means in a language where a
field is a node with an id, not a name: two cases' `to` fields are two
nodes. Either the type declares the shared field once (a field of the
type, which every case listed has), or "same name and same type" decides.
The first keeps names out of meaning (the project's rule), so it's the
recommendation, and it wants a short design note before code. Prior art:
Haskell's field selectors over several constructors (partial: they throw
on a case without the field, which Choice replaces), and OCaml's inline
records.

## 3. Literal choices

machine's `instruction of` (21 arms on the op's name), `folded` and
`arith` (on "add", "sub", "mul"), `options of` (on "--profile", …), and
board's `stage from key` and `on key` are all `if x = "a" then … else if
x = "b" …`. L164b's `case of` writes them as a list of pairs; L164c (a
match with literal arms, drawn as a match) is the change that makes them
read as what they are. Two programs out of two have the shape, so L164c is
raised from P3 to P2.

`stage from key` is also `stage key` backwards, and
`first(inverse(stage key, "doing"), else todo)` gives `doing` today: a
program that writes a table once and reads it both ways needs nothing new.

## 4. Library gaps

- **Text has no `contains`, and no "the rest after a prefix" (L169).**
  board's `contains words` writes `first(not (find(lowercase(title),
  lowercase(w)) < 0), else false)`; `find` is a Choice of positions, so
  the test is "some position exists", spelled backwards. machine writes
  `slice(word, 1, length(word))` five times, and board twice, each right
  after `starts with(word, "r")` or `"#"` or `"+"`. Proposal: `contains
  text(t, part) -> Bool`, and `after prefix(t, prefix) -[Choice]-> Text`
  (the text without the prefix; no answer when it doesn't start with it),
  which is `starts with` and `slice` as one Choice, the way the language
  reads "if it's this shape, the inside".
- **No `change(cell, f)` (L170).** board writes `write(stc, f(read(stc)))`
  six times (`undone`, `redone`, `do edit`, `tick` twice, `loaded`).
  `change(cell, f) -[Cells, Diverge, Update, e]-> Unit` is that, as one
  call, the way `write at` is one call for a place inside a cell.
- **No random whole number or random item (L171).** board picks a card
  with `nth card(cs, random below(as float64(length(cs))))`, comparing a
  Float64 position against 1 and counting down. `random item(list)
  -[Random, Choice]-> a` (no answer for an empty list) says it.
- **A printer's reader is written by hand (L172, P3).** board's `card
  line` prints a card as `1|todo|2|0|a,b|title` and `read card` reads it
  back; machine's `disassembled` and `instruction of` are the same pair.
  `inverse(card line, "3|doing|2|0|a,b|Hello")` is refused because it may
  not end (Diverge). The step that's missing is that `joined(parts, sep)`
  run backwards is `split` when no part holds `sep`, and ends, because each
  part is shorter than the text (MODES.md). Worth doing only after the
  rest; it's the language's best answer to "write the format once".

## 5. What the programs could use now

The library grew today (L161, L162, L162b, L164) partly because of these
programs, and they haven't been brought up to date. None of this is a
language change; it's one adoption PR (L173):

| program | definition | now |
|---|---|---|
| machine | `args mapped` (19 arms) | `fields mapped` (L162b, which was built for it) |
| machine | `op name` (21 arms) | `case name` (L162) |
| machine | `all digits` | `all pass` plus not empty |
| machine | `zeros` | `copies(n, 0)` |
| machine | `as set` (its own) | the prelude's `as set` |
| machine | `code problems`, `op counts`, `without nops` (two lists walked together) | `zipped` |
| machine | `instruction of`, `folded`, `arith`, `options of` | `case of` (L164b), until L164c |
| board | `tag in` | `contains` |
| board | `card of` | `first where` |
| board | `position of` (its own, 0 when missing) | the prelude's `position of` (none when missing) |
| board | `nth card` | `item at` |
| board | `stage from key` | `inverse(stage key, k)` |

board's own `position of` has the prelude's name and another type, so a
reader of board sees two `position of`s. That one is the program's to fix
by using the prelude's.

## 6. Two that are the text reader's

- **A case can't be named as a function.** machine has 17 definitions
  like `‹make add›(into, a, b) = add(into, a, b)`, only to pass a case
  where a function goes. The checker types a case's name as its
  constructor function (infer.ts, variant refs), but the text reader says
  "nothing is named out here" for `map([number(1)], out)`. E212: read a
  case's name as a value; and E211 above asks the palette the same.
- **A field read names the wrong type.** `jump(number(3)).to` in machine
  says "to belongs to one case of Attribute": the reader picked the html
  library's `Attribute.to`, not `Instr`'s. E213: resolve a field read by
  the type of what it reads. (After L168 the read is allowed; the wrong
  name is a bug either way.)

## Checked and fine

- Effects read well in both: machine's `Abort` from the assembler to
  `main`'s one handler, and `Diverge` exactly on the worklist and the
  optimizer's rounds. board's handlers are typed by `Handler`'s row.
- Tuple results (`tuple(code, lines) = ‹code of›(…)`) and the Choice
  idioms (`first(…, else …)`) carry both programs.
- `inverse` on a finite match ends and has one answer (§3).
