## The verdict, first

389 PRs landed since R3, 65 rows of them on 31 October alone: three
Clifford demos, std's Array and the two-ended buffer on four targets, the
chooser storing lists as arrays, the compiled preview, staging, jets, and
a compiler speed round. **All five of R3's todo tests pass now**: an exact
total order for `compare`, private constructors, and Ints that know they
are Ints all landed. That was the hardest list any review has handed over,
and it was done properly.

The new risk is a different shape. The project now has several engines for
one program (the evaluator, the evaluator with jets, compiled JS, compiled
JS after staging, WebAssembly, C, WGSL) and, in front of all of them, a
chooser that rewrites the program into another representation without the
program asking. Each piece is tested against its own definition. Nothing
checks that the pieces agree with each other on whole programs, and the
first three findings are all in those gaps:

1. **The chooser breaks a gallery example.** Since #769 (C30d3b),
   `chapters` doesn't run or compile from `lab` at all: the chooser picks
   `array of List`, and the rewritten program fails the type check because
   `keep` is pinned to `List`. The editor's Run calls the same chooser.
   Every suite stayed green, because no test runs an example through the
   chooser. §1.
2. **The two-ended array's costs are true only when no one shares it.**
   `array of List` says cons is constant. A cons onto a match's rest copies
   the whole array, so a stack (match, then cons) is quadratic: 16,000
   steps take 6 s, against well under a millisecond as a cons list. The
   chooser picks the array by itself, and since 2026-10-30 a program can't
   say no. §2.
3. **Compiled code and the evaluator disagree on ∞ and NaN, on purpose.**
   Staging (C65) turns `0 · x` into `0` and `x + 0` into `x`, "as compilers'
   fast-math does". The evaluator keeps NaN. Since #789 the editor's
   preview swaps from the evaluator to compiled code a few seconds after
   opening, so a page can change its answer under the user. §3.

## 1. The chooser refuses `chapters`

**Repro.** From `ters/`:

```
$ node cli/lab.ts run examples/chapters book.md out
lab: chapters doesn't check on List as array of List: keep is pinned to
(List a, (a) -[Choice]-> Bool) -> List a, and this makes it
(Array a, (a) -[Choice]-> Bool) -> Array a
$ node cli/lab.ts compile examples/chapters -o x.mjs      # same message
$ node cli/lab.ts run examples/chapters --as-defined      # runs
```

It compiles at `929d856^` and fails at `929d856` (#769, C30d3b, "the
preview's chooser stores lists as arrays when their jobs say so"), and it
still fails at `44250db`. The editor's Run goes through the same
`withLibraryRepresentations` (editor/runWorker.ts line 64), so Run on
`chapters` most likely shows the same error; QA12 opened every example but
`chapters`' main needs two files, which may be why it didn't show.

**Why it matters more than one example.** Ersagun's rule since 2026-10-30
is that the compiler always chooses and a program never pins a
representation. That rule is only safe if the choice can never make a
working program fail. `listBoundary` (library-reps.ts) looks for places a
list can't become an array (builtins, `solve`, the library's own
definitions) but not for a signature the program pinned. And when the
rewritten program fails to check, the error goes to the user, who has no
way to answer it.

**Why no test caught it.** `agreement.test.ts`, the round-trip tests and
the page tests all run the examples as defined. Nothing runs each example
the way `lab run`, `lab compile` and the editor do, after the chooser.

**Fix, in order.** (a) A choice that doesn't check is not a choice: when
the rewrite fails the type check, keep the definition as written (and say
so in the chosen-representation note E159 will show), never refuse the
program. (b) `listBoundary` treats a pinned signature with a `List` in it
as a boundary. (c) A test that runs every example's `main` through the
chooser, evaluated and compiled (this is also §7's test).

## 2. A two-ended array's cons is constant only when nothing shares it

`std.ts` `pushFront` writes into the slot before a view's start when that
slot is the buffer's lowest used one (`v.start === b.lo`), and otherwise
copies the whole view. That is right: the slot may hold an item another
view still sees. But it means a cons onto a **rest** always copies, since
the rest starts one past the buffer's low end. `array of List` lists cons
as `constant` (array-list.ts), and REPRESENTATIONS.md and CREDITS.md say
"cons, match and length constant".

**Repro** (std's Array directly, the evaluator's and compiled JS's code):

| n | n × (rest, then push front) | n × push front |
|---|---|---|
| 1,000 | 24 ms | 0.2 ms |
| 4,000 | 166 ms | 0.4 ms |
| 16,000 | 6,003 ms | 0.6 ms |

Quadratic. Match-then-cons is the most common thing a list program does:
a stack machine, a parser that pops and pushes, replacing a list's head,
any `x :: rest` built from a match. As a cons list it is constant. The
chooser weighs the costs the row states, so a program that also asks for
`length` or `item at` (constant on the array, linear on a cons list) tips
toward the array and gets slower, without a way to say no.

The same sharing shows in memory: a rest is a view on the whole buffer, so
after a million `rest`s the one-item array left still holds a buffer of
1,572,864 slots (Go's slices have the same leak, which is why Go has
`copy`).

C avoids the copy where it can: CREDITS.md says a C view nobody else holds
is reused, as Perceus does. The evaluator, compiled JS and WebAssembly
(wasm-rt.ts `array.pushFront`, the same test on `lo`) can't know that.

**Fix.** This is Ersagun's design, and the buffer is right; what's wrong is
the cost the chooser is told. Options: (a) the row says cons is constant
only onto an array nobody else holds, and the chooser counts a cons onto
a match's rest as linear (the chooser already reads the program's jobs, so
it can see `cons(x, rest)` inside a match arm); (b) a measured test per
row: run each job at n and 4n and check the ratio against the cost
claimed, so a cost table can't drift from the code again. (b) is cheap and
catches the whole class; (a) fixes this case.

## 3. Staging changes what Float64 means

stage.ts, at the top: "For a later x that is ∞ or NaN, 0 · x is NaN, not
0; staging assumes finite numbers, as compilers' fast-math does." It also
simplifies `x + 0` to `x`, which differs for x = −0. Staging only runs when
compiling (compile.ts, scalar.ts), never in the evaluator.

So the same program gives NaN evaluated and 0 compiled, whenever a part
known to be 0 meets a later ∞ or NaN. In the Clifford demos that is not
far-fetched: a PGA meet of two parallel lines is an ideal point (weight 0),
and normalising it divides by 0. Since #789 the editor's preview shows the
page interpreted and swaps to the compiled page a few seconds later (§5),
so the user can see the value change.

By the two-landscapes rule (2026-10-24: a target's weirdness must never
dent the language's ideas) this is backwards: a compile-time convenience
decides what `·` means. Fast-math is a flag in C compilers because it is a
different language.

**Fix.** Fold `0 · x` only when x is known finite (a literal, or a part the
staging knows), keep it as a multiply otherwise; `x + 0` → `x` only when x
can't be −0, or not at all. The products the demos stage have the zeros
known on both sides, so most of the gain stays. Then a test that compiles
a staged product with ∞ and NaN inputs and compares with the evaluator.

## 4. `clifford inverse` is the versor inverse

prelude-source.ts: `clifford inverse(al, v) = ṽ / ⟨v ṽ⟩₀`. That is the
inverse when v ṽ is a number: versors and blades, which is what the demos
pass. For a general multivector it is wrong. In Cl(3, 0) take v = 1 + e₁:
ṽ = 1 + e₁, v ṽ = 2 + 2e₁, the scalar part is 2, so the function returns
(1 + e₁)/2, and v times that is 1 + e₁, not 1. In fact 1 + e₁ has no
inverse at all ((1 + e₁)(1 − e₁) = 0), so the right answer is "none".

`clifford inverse` has no doc string (every other clifford function has
one), the blade-mask rule in grades.ts gives it mask(ṽ) (true only under
the same assumption), and `reflect` and `project` call it (fine, they
take vectors and blades).

**Fix.** Either rename it to say what it is (`versor inverse`) and give it
a Choice answer that is empty when v ṽ isn't a number, or make it the
general inverse (closed forms exist up to n = 5: Hitzer and Sangwine,
2017) and keep the cheap path for versors. Doc string either way, and
credit whichever formula is used.

## 5. The compiled preview restarts the page

#789 (I97) is a good change: Bounce's preview went from 7 to 60 frames a
second. Two seams remain:

- **The swap starts afresh** (main.ts `swapCompiled`: "the compiled page
  takes its place when it's ready, started afresh"). For 2 to 7 s the user
  sees a live, interpreted page. A slider moved, a die thrown, a point
  dragged in that time is gone when the compiled page mounts. The status
  line says a swap will happen; it doesn't say what will be lost. Handing
  the page's cells across (both engines keep cells the same way) or holding
  input until the swap would close it.
- **Pages with sound stay interpreted** (`hasSound`). That is a special
  case the user can't see: the pedal's preview is slow for a reason
  nothing on the page explains. It goes away when the audio page can run
  compiled code, which `lab render --compiled` already does.

## 6. Process

**Check main mostly doesn't run.** Of its last 60 runs, 49 were cancelled
(GitHub keeps only one queued run per concurrency group, so a merge that
lands while another is running replaces the one waiting), 4 failed and 5
passed. Nothing is skipped: each run tests everything since the last green
one, which is sound. But:

- a run takes about 19 minutes (`timeout-minutes: 20`), so one more slow
  test file turns every run into a timeout;
- "affected" reached 93 of 97 projectional test files on 31 October, so
  testing only what changed no longer saves much; with most changes
  touching std.ts or the prelude, nearly everything is reached;
- the four failures (for example `forward and backwards agree: spacetime`,
  `combined speed(0, 0)`, at #802) were fixed by later merges, but the
  memory note says notices of failures never arrive, so a red main is only
  found by whoever happens to look.

Suggested: the lanes check Check main's latest run when they start an
item (one call), and the T lane looks at why std.ts and the prelude reach
every test (a test of `clifford exp` shouldn't need the whole library
reloaded to be "affected" by a change to Map).

**Twenty tasks a day is a lot of surface.** 65 rows finished on 31
October. The two high findings above both came from that day and both got
through green suites. This isn't a call to slow down; it is a reason for
§7's test.

## 7. Complexity: engines that don't check each other

The ways to run one program:

| engine | where | checked against |
|---|---|---|
| evaluator | run.ts | the meaning |
| evaluator with jets | jets.ts | each jet against its definition (jets.test.ts) |
| compiled JS | compile.ts | the evaluator, per feature test |
| compiled JS after staging | stage.ts | clifford.test.ts on a few values |
| WebAssembly, C, WGSL | wasm*.ts, c*.ts, wgsl.ts | per feature test |
| any of these after the chooser | library-reps.ts, represent.ts | library-reps.test.ts on small programs |

And one data structure is now written five times: std.ts `ArrayView`,
runtime.js (shared), wasm-rt.ts in hand-written WAT, c-rt.ts, and WGSL's
fixed-size copies. wasm-rt.ts and wasm-math.ts are 12,500 lines between
them. The aim in REPRESENTATIONS.md is the opposite: an array written once,
in the language. That's fine as a staging post, but each new structure
(C63's hash table is next) will cost five again.

**One test would have caught §1 and §3:** for every example, run `main`
(text) or the page's first render through the evaluator as defined, the
evaluator after the chooser, and compiled JS after the chooser and staging,
and compare. This review's script did the text half in a few minutes and
found §1 on its first run.

## 8. What held up

Worth saying, since most of this doc is holes:

- **Shader Ints** (C66c1) check every i32 operation for overflow (Hacker's
  Delight 2-13) and give up as a budget does, instead of wrapping. That is
  exactly the two-landscapes rule applied well.
- **Jets** are pinned to the definition's hash and tested against it, so a
  changed prelude can't keep a stale jet.
- **The two-ended buffer** is the same logic in JS and WebAssembly (read
  side by side): every value still never changes.
- **`clifford exp` by series** (I92) is scaling and squaring with Horner's
  form, credited to Moler and Van Loan; the term count is enough for the
  sizes the demos use.
- **R3's whole list** was done, one PR at a time.
