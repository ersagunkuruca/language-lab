## 1. Main red for 16 hours (high)

Check main's last 40 runs, newest first: 4 green (since `d2945bc`), then
31 failures and 4 cancellations back to 2026-11-15 15:31, then green. Over
those 16 hours, 42 commits landed on main. They include rows C228 to C250,
I291 to I307 and L261.

WORKFLOW's rule (and the 11-01 lesson behind it) is that a red Check main
is the merging lane's next job. Two fixes did land on 11-15 for earlier
reds (#2702, #2720). This time, all three lanes kept merging. Without a
green main, the covering-tests-only rule loses its safety net. A break
that a covering test misses goes in under 41 other changes, and its blame
step can't name a commit.

What failed: in the last red run (`9b00be0`, run 43789239732) two shards
failed with one file each. Shard 3's was `resolve-once.test.ts`, a
deepStrictEqual on the library's resolved lists. Its blame found no one
commit. It passes alone today. That is an order or state dependence
between test files, the kind E-picks2 fixed once by keying a cache on the
nodes object. The 4 green runs since don't show it is fixed, only that it
didn't fail.

**Fix:** a lane that sees main red for more than an hour stops merging
until it is green or the failing file has a row. Also add a row for
resolve-once's dependence on the files run before it in the same process.

## 2. A run still types the whole library (medium-high)

```
cold (LAB_NO_LIBRARY_STORE=1)   warm (.lab stores filled)
ters check  wc   2.5 s           0.9 s
ters run    wc   4.5-5.0 s       1.2 s
run --evaluator  4.9 s           2.0 s
```

The CPU profile of a cold `ters run` (4.2 s): `infer` 2.2 s in all.
`shareFoldItems` (compiler/src/fold-items.ts) accounts for 1.6 s: it
calls `parallelFolds` (ters/src/lang/pure-branches.ts), which loops over
`Object.values(code.nodes)`, every library fold included. For each one it
calls `ownEffects`, which asks `info.typeOf.get`. The first such ask on a
library node makes `libraryLater` type the whole library. With
`NO_FOLD_ITEMS=1` the run takes just as long, so other passes ask
the same way. Fold-items is only the first to ask.

The R11 todo test shows it in a process: a `main` that prints one text is
checked with no library body typed, and after `compiledDefs` for `main`
every body is typed.

The warm numbers depend on `.lab/runs`. Its keys hold `graphHash`, the
compiler's and checker's own sources, so every edit to a pass makes the
next run cold again. That is what a lane, the MCP and the editor hit
while the code is changing. QA's I308 ("Where it runs" takes 6 to 8 s on
each program opened) is probably the same cost in the editor. That is
not measured here.

**Fix:** a pass walks the nodes `main` reaches, not `code.nodes`
(`shareFoldItems` already computes `reached`, after `parallelFolds`
has asked about everything). Then the R11 test passes and R10's guard
covers a run too.

The biggest additions this week: c.ts +2.7k, scalar.ts +2.3k, wasm-rt.ts
+1.7k, c-layout.ts (new) 1.6k, std-ids.ts (new) 1.6k, branches-rt.ts (new)

The cost is how they were built: the same rewrite, row by row, for each
place a list can live. "Consing onto a call of itself is a loop" is C232
for a tree's lists, C240 for arrays, then C250 for the list of one it left
behind. "Appends onto what a loop carries" is C233. "A hash table's key
may be data" is C243b for C and C243c for WebAssembly. Each one is right.
Together they are FOUNDATIONS' warning: one mechanism written once per
representation and per target.

P7 (a foundation row every fourth item in each lane) is still open, and
this week's rows were speed, pages and editor rows. Test reach is now measured by the line map
(T16): a one-line comment edit to text.ts runs 0 files before merge and
4 after, against 139 of 219 on 11-13. That is cheaper, and it puts more
weight on Check main (§1).

**Fix:** before the next speed round, one row that gathers the
per-representation loop rewrites (C232, C240, C250, C233) into one rewrite
over the list interface, measured on pack and scan as they stand.

## 4. Depth and the evaluator (low)

Two probes, both well typed, on the evaluator and compiled JavaScript
(`compiledDefs`):

- `sum(n) = if n < 1 then 0 else n + sum(n − 1)`, not a tail call: at
  n = 10⁶ the evaluator gives 500000500000 in 4.4 s, and compiled JS in
  0.44 s. No stack error on either.
- A Peano number built 10⁶ deep (`s(s(…z))`), then counted back with a
  non-tail match: 1000000 on both, in 7.4 s and 1.2 s.

That is a real change from R1's stack limits. What's left is speed. The
evaluator is 6 to 10 times slower than compiled JS here. The `numbers`
example, as written (Peano Nat), still can't be run by the evaluator
(core-js.test.ts: "the evaluator runs out of memory and the printer's
recursion out of stack"). It is checked only after its Nat is stored as
an Int. That's a measured limit, not a crash a user meets: `ters run` stores
it the same way.

## Is it still on course?

On course for regular programs (wc, pack, scan, the gallery all run
compiled on four targets), shaders, web pages (pages now carry only what
`main` reaches, C251, #2789/#2797) and mobile (native Android, iOS built).
The risk has shifted. It is no longer missing pieces. It is the speed
of change against the safety net: rows close in minutes, covering tests
reach less by design, and main stayed red overnight while 42 changes went
in.

## Recommended order of fixes

1. **Main's red rule** (§1): stop merging when main has been red over an
   hour, and add a row for resolve-once's dependence on other test files.
2. **R11 §2** (§2): passes walk what `main` reaches. That gives a cold run
   about 1.5 s back, and probably helps I308 in the editor.
3. **One loop rewrite over the list interface** (§3), before the next
   speed round. Name it P7's next foundation row.
4. **`numbers` as written in the evaluator** (§4), once 1 to 3 are done.
