# Ters programs in a real git repository (2026-11-14)

I241. I (Claude) kept two programs, `dice` and `pig`, in a repository of
their own, [ersagunkuruca/ters-trial](https://github.com/ersagunkuruca/ters-trial)
(branch `claude/project-thread-fhnqf0`, 14 commits, 5 of them merges), in
the saved format of I240 (one node per line,
[SAVED-FORMAT.md](../design/tools/SAVED-FORMAT.md)). Every edit went
through the MCP's `Session` (`replace`, `rename`, `comment`, `define`), as
an LLM or the editor would make it, never by hand, except where a conflict
was resolved in the JSON on purpose. Then I used git as a team would:
branches that change the same definitions, merges with and without the
driver, a folder moved while another branch edited it, a rebase, `git log
-p`, `git blame`, and GitHub's own view of a commit. Findings are Inbox
rows I265 to I272 in BACKLOG.md.

## Set-up

- `node ../language-lab/ters/cli/ters.ts git-setup` in the clone sets
  `diff.ters.command` and `merge.ters.driver`. It points at this
  language-lab checkout and this Node by absolute path.
- `.gitattributes` has to be written by hand. Language-lab's names
  `ters/examples/**`, so it can't be copied; the trial first used
  `programs/**`, then `**/code.json` and friends (see "Moves" below).
- A clone that never ran `git-setup` is a plain git repository: an
  attribute with no driver configured falls back to git's own diff and
  merge. Nothing breaks for someone without Ters.

## What works well

- **An edit reads as the edit.** A literal changed (`6` → `8`) is one line
  of `code.json`, and a rename is one line of `names.default.json`, in
  `git diff --no-ext-diff`, in `git log -p`, and in GitHub's commit view.
- **`git diff` prints `ters diff`.** After `git-setup`, `git diff`,
  `git diff --staged` and `git log -p --ext-diff` show definitions with
  their old and new lines, renames as one line (`renamed `two dice` to
  `pair``), comments with both texts, and added definitions with their
  types. A side file whose `code.json` also changed says "(shown with
  code.json)", so nothing is printed twice.
- **git's own line merge works on most changes.** Two branches that
  changed different nodes, a rename on one and an edit on the other, a
  comment on each, a moved folder against an edit at the old path: all
  merged without the driver. A real conflict (one literal set to 250 on
  one branch and 300 on the other) was one node on each side of the
  markers, easy to resolve in the JSON by hand.
- **The driver merges what lines can't.** Two branches that each add a
  definition conflict in git's line merge (both append to `defs`); the
  driver merges them as an ordered set. A rename to two different names
  and a literal set to two values were each reported by definition:
  `` `wins for B`: both changed it (ours "wins for B", theirs "B's wins") ``.
- **Results stay canonical.** After every merge, line or driver, loading
  each program and saving it again changed no byte.
- **Per-node history for free.** `git blame code.json` dates each node,
  and follows the folder's move: the `300` in `a hundred rolls` blames the
  move commit, its call node the initial commit. `git log -S<id>` finds
  the commits that touched one node.
- **Rebase and cherry-pick** need nothing special: a rebased commit read
  the same in `git log -p --ext-diff`.

## What's rough

1. **A conflict can lose a change while saying "ours kept" (I265).** One
   branch set die's `6` to `8`; the other retyped die's body
   (`floor(random() · 6) + 0`), which made every node under it new. The
   driver said `` `die`: node reso…: theirs removed it and ours changed it ``,
   "ours kept". It kept our node, but the call above it took theirs' new
   children, so the kept `8` was reachable from nothing: the merged
   program read `· 6`, and the dead node stayed in `code.json` until the
   next save. git's line merge had the same one-node conflict and the same
   outcome once resolved. A "both changed its value" message also doesn't
   say the two values (the name conflict does).
2. **Retyping an expression gives every part a new id (I266).** The MCP's
   `replace` with text keeps the root's id but makes all its parts anew,
   even ones that read the same (`floor`, `random`, `6`). That turns two
   unrelated edits to one definition into a conflict, as in 1, and makes
   a one-character change many lines (`+ 1` → `+ 0` was 37 lines of
   `code.json`, though `ters diff` showed it as one line).
3. **After the merge prints, the conflicts are gone (I267).** The driver's
   message is the only record. The file is clean JSON with ours kept, so
   nothing in it says where to look, and git's combined `git diff` during
   a merge never calls an external driver: it shows raw JSON. Resolving
   meant `ters diff <program> --from MERGE_HEAD` and reading carefully.
   Merge commits likewise show raw combined JSON in `git show --ext-diff`
   (`ters diff --from HEAD^1` works).
4. **A moved folder isn't followed (I268).** After `git mv programs/dice
   games/dice` and one edit, `ters diff --from main` printed all of dice
   as added and never mentioned `programs/dice`: `git diff --name-only`
   detects the rename and lists only the new path, and `ters diff`
   reads the old version at the new path. `ters diff games/dice --from
   main` does the same. The git driver did follow the move, but headed
   the files with the old path on both sides, and said "no changes to the
   program (only its layout or formatting)" for files that only moved.
5. **Attributes are tied to paths (I269).** With `programs/**` patterns,
   the moved `games/dice` lost both drivers silently: the next merge into
   it used git's line merge. `**/code.json` patterns fix it, but
   `git-setup` neither writes nor checks `.gitattributes`, and
   language-lab's own patterns would miss a program anywhere else.
6. **`ters` on a file with conflict markers crashes (I270).** `ters check`
   printed Node's `SyntaxError: Expected double-quoted property name …
   (line 796 column 1)` and a stack. It should say the file has git
   conflict markers and where.
7. **GitHub's merge button can't use the driver (I271).** It never runs a
   custom merge driver, so two pull requests that each add a definition
   conflict there at the end of `defs`, which the CLI driver would have
   merged. Everything else above merged on lines and would merge on
   GitHub too.
8. **Ters needs a language-lab checkout (I272).** `git-setup` points at
   it by absolute path; there is no `ters` to install, so a teammate (or
   CI) needs the whole lab cloned beside the repository.

Two smaller things, not about git: `ters check` lists a value
`goal = 100` as `goal : a`, where the MCP's view says `a where a is a
Number`; and I couldn't open pull requests in ters-trial, since this
session may push one branch only, so "PRs read in GitHub's raw view" was
checked on commits instead (GitHub's view of a commit is the same patch).
GitHub's view shows node ids, never which definition changed; the PR
comment with `ters diff` that would answer that was declined on
2026-11-13 (DIFF.md).

## Verdict

The format does what I240 promised: edits read as one line, history is
per node, most merges need nothing, and the tools agree with each other.
The rough parts are around conflicts (1, 3, 6), moves (4, 5), and ids
that don't survive retyping (2), which feeds the conflicts. 1 and 2 are
the ones that can lose a change, so they come first.
