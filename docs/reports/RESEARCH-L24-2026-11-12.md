# L24: the research row, 2026-11-12

L24 kept three research items from the first review's roadmap (REVIEW.md §9,
ROADMAP item 8), to take up "as they become blocking":

1. costs worked out from folds,
2. laws proved by fusion,
3. fast invertible parsing.

For each item, this report asks whether an example is blocked by it today,
and what concrete work, if any, it points to. In short, parsing was the
only item still costing something. It is now linear in the interpreter and
fast on WebAssembly and C up to the stack limit, and that limit is one new
row (I221). The other two items block nothing.

## 1. Costs worked out from folds

**What exists.** Each representation declares the cost of each of its jobs
on NUMBERS.md's ladder (`1`, `log n`, …, `n²`). The chooser (represent.ts)
and the way picker (ways.ts) add these costs up on one scale (cost.ts).
NUMBERS.md "Costs and the chooser" planned two improvements. Declared
costs that get checked are built: rep-costs.test.ts (I106b) runs every job
of every representation row at sizes n and 8n, and checks the growth
against the row. Costs worked out from a job's folds, in place of declared
ones, are not built.

**Is it blocking?** No. No example's choice is wrong because a cost was
declared. The one case where a declared cost hid a slow job (`tree of
List`'s fold, REVIEW-2026-11-01b §4) was a slow job, not a wrong cost: the
cost was declared correctly, and the job was fixed (C75). Worked-out costs
would save a representation's author from writing the cost column, and a
test already checks that column.

**Work.** None now. If a representation written by a program (not the
library) gets a declared cost wrong in a way the measurement test can't
see, that is the example that makes this item worth doing.

## 2. Laws proved by fusion

**What exists.** A representation's laws are tested, not proved. Each job
at R must agree with T's own through `meaning`, on small values built by
T's jobs (rep-laws.ts, L108d). The match and fold cases are checked the
same way (L108d2). Embeddings' laws are tested the same way (embed-laws.ts),
and the prelude's laws are tested compiled too (T7e3). A proof by fold
fusion would show `meaning ∘ job_R = job_T ∘ meaning` once for all values,
when both sides are folds, by checking one equation per case.

**Is it blocking?** No. Searching DONE.md finds no law broken in a way the
small-value tests missed. The failures recorded there are the solver's
rounding (T7e14d) and searches that run long (T7e14e), and a proof
wouldn't change either. A proof needs an equational prover over the
language's terms, which doesn't exist yet, and it is a large step.

**Work.** None now. The trigger would be a representation whose law fails
only on values too large for the tests to build.

## 3. Fast invertible parsing

This item was still costing something. "The printer is a parser"
(BACKWARDS.md): `show numbers`, run backwards on a text, reads the numbers
back. The first review measured 400 numbers in 228 s, about cubic. Since
then, tabling and `fits` pruning made the interpreter much faster, and
C195h compiled the search to WebAssembly and C. This round measured
examples/backwards' `read numbers` on texts of n numbers. The example's
fuel was raised for the measurement, since its 10,000 steps stop near
1,000 numbers by design.

Interpreter times are a whole `ters run` of the example, of which about
2.6 s is startup and the example's other lines. WebAssembly times are
the run alone.

| n numbers | `ters run` before | `ters run` after | WASM before | WASM after |
|---|---|---|---|---|
| 2,000 | 3.4 s | 2.6 s | 163 s | 0.2 s |
| 5,000 | stack overflow | 2.6 s | not run | 1.2 s |
| 20,000 | stack overflow | 3.1 s | out of memory | stack overflow |
| 300,000 | not run | 14.5 s | not run | not run |

What was fixed (this PR):

- **The answer handed back recursed per item.** relate.ts's `toValue`
  turned the list read back into a value with one JS call per item. It
  also checked the rest for unknowns at every item, which was quadratic.
  It overflowed the stack near 5,000 numbers. Now it checks for unknowns
  once and builds the value with its own stack.
- **Each item read tried every cut of the rest.** `fits` rules out cuts
  whose front can't be a number shown, but the loop still tried every cut
  of the rest, so it was quadratic. `fits` now also says where no longer
  front can fit (`past`): a number shown has no space, so in
  `show(n) ++ " " ++ rest` the front ends by the first space plus the " ".
  The cut loop stops there. A whole run on 20,000 numbers went from 47 s to 17 s.
- **A suspended search took its waiting goals apart at every step.**
  `suspendBind` keeps the goals after a suspension as a list. Each time
  the search suspended again, it rebuilt that list one goal at a time,
  once per item for every item, which was quadratic and was a third of
  the run in the garbage collector. The goals now wait on as they are: a
  run of goals followed by another run, laid out in order only when an
  answer comes. A whole run on 20,000 numbers went from 17 s to 3.1 s, about half a second past startup.
- **Compiled code built every cut of the rest.** The same bound, written
  into the cut list (scalar.ts): the cuts stop at the first space plus the
  joined text after the number. This reduced 2,000 numbers on WebAssembly
  from 163 s to 0.2 s.

The answers and their order are unchanged. The cuts no longer tried could
never pass the check that follows, and the goals run in the same order as
before. examples/backwards prints the same as before, in `ters run` and on
WebAssembly.

What is left is one new row:

- **I221.** Compiled relational streams nest one bind per level, and
  forcing a pause goes through all of them. Reading back 10,000 numbers
  on WebAssembly overflows the stack, and the time grows faster than n
  (0.2 s at 2,000, 1.2 s at 5,000). relate.ts had the same problem (L18)
  and fixed it by keeping the goals after a suspension as a list, as
  above. Compiled code needs the same fix: a pause in a recursive mode
  function should carry the binds waiting on it as data, not as closures
  nested inside each other.
