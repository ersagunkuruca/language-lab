# L254: lazy fold results, 2026-11-13

LANGUAGE.md's "What's next" listed **laziness for fold results, so effects
in folds could run top-down**. A fold computes its children's folded
values before the parent's case runs (run.ts `fold`, children first), so
an arm that prints and then uses its result prints the last item first.
L254 asked for research before any building: what lazy results would
mean for Choice and for the compiled loops.

In short: **don't make fold results lazy.** No example needs it.
Top-down order can already be written, and the compiler already gets the
part of laziness that costs nothing. Making results lazy would change
which answer a Choice gives first and which Abort wins, and it would take
away the loops and the parallel folds the compiler builds today. The item
is closed. It comes back as a new row if a program needs world effects in
a fold, in an order that recursion can't give.

## 1. What the examples do

Every fold in the examples (87, in their own definitions), with the
effects of what its arms call:

| effects in the arms | folds | where |
|---|---|---|
| none | 77 | |
| Choice | 5 | agent `a star`, algebra `simplify`, bounce `off the walls`, chapters `sections`, countdown `permutation` |
| Diverge | 4 | collatz `steps of all`, `most steps`, `walks of`; fingerprint `fingerprint of` |
| Abort | 1 | calc `evaluate` |
| Console, Files, Network, Random, Time, Cells | 0 | |

None of these is an ordered world effect, the kind whose order a person
would see (a line printed, a file written, a cell set). So no example is
blocked by the bottom-up order.

## 2. Top-down order can already be written

There are two ways, and the checker sees both end:

- **Recursion on the rest.** `for each` and other functions written this
  way recurse on a piece of their input. The termination check accepts
  that as structural (LANGUAGE.md "Loops"), and the arm's effects run
  before the call on the rest.
- **A fold whose value is a function.** Each arm returns a function, and
  calling a child's result is the step down: `fold xs` with
  `nil → (d) ↦ …` and `cons(x, rest) with r → (d) ↦ (…; r(d + 1))`, then
  applied once. Six examples fold this way already: queens' `safe` (in all
  four queens programs), langford's `free` and numbers' `fold Nat′`. The
  Blocks view writes such a fold applied at once as `fold placed from
  distance = 1`. Each arm's work, effects included, runs when the arm's
  function is called, parent before children. It compiles: queens' `safe`
  is one of the C benchmarks (C207m).

So "top-down effects in a fold" is the second form. What laziness would
add is not writing the `(d) ↦` and the `r(…)`.

## 3. What lazy results would change

**Choice.** A lazy result shared by two uses must pick once per branch of
the search. This is Curry's *call-time choice* (González-Moreno et al.,
"An approach to declarative programming based on a rewriting logic",
JLP 1999; López-Fraguas, Rodríguez-Hortalá, Sánchez-Hernández, "A simple
rewrite notion for call-time choice semantics", PPDP 2007). Today's
strict fold gets this for free, because a result is a value before the
arm runs. Lazy results would need a memo per branch: the evaluator's
streams would carry a thunk's answer per alternative. They would also
change *when* each choice is made. The search order Ersagun decided
(c195f: fair, interleaved, with compiled code reproducing it) would then
give the five Choice folds' answers in a different order. Their accepted
answers in examples.json, and what `first` gives, could change.

**Abort.** Which failure is seen first would change. In calc's
`evaluate`, an expression with two failing parts reports the first
child's failure today, because the children are folded first, in order.
Lazily, it would report whichever failure the arm reaches first.

**Diverge, termination.** No change: a fold ends either way. A result
that is never used is never computed, so a lazy fold can only do less.

**Costs.** Representation costs (NUMBERS.md's ladder, rep-costs.test.ts)
are declared for the whole traversal. Under laziness they become upper
bounds, which the chooser can live with. It is still a change to what a
cost means.

**Running backwards.** Folds run backwards through relate's equations
(BACKWARDS.md). Those equations are strict: each result is a value
between two cases. A lazy result has no place there, so a backwards run
would need the strict fold kept beside the lazy one.

**The world log.** A page's log (I239) records the world's answers in the
order they are asked. Lazy results change that order, not what can be
replayed, so the log would still work.

## 4. The compiled loops

The core IR lowers a fold to a loop over a stack of the values on the way
down (scalar.ts `framesOf`). Several compiler passes depend on children
first and on each item's work being independent:

- `fold-items.ts` (C42e) splits each item's work into a map that runs on
  many items at once.
- `fold-chunks.ts` (C42h) counts items in runs, one per thread on C.
- `early-and.ts` (C207m) stops a Bool `and` loop once it is false.

Lazy results would turn the loop into a chain of thunks or closures, with
the stack depth and allocation that brings. The two parallel passes would
stop applying wherever an arm could have effects. That is exactly the
case laziness is meant for.

Where the arms are pure, the order can't be seen, and the compiler
already takes laziness's gain. scalar.ts computes **a result used once
where it is used**, so "an arm that doesn't need it (insert, once it found
the place) stops there". It keeps the evaluator's order only under a step
budget, where the count would differ. early-and.ts stops a Bool fold at
its first false. Both are short-circuiting found by analysis (McCarthy's
conditional `and`), with no change to what the language means.

## 5. Recommendation

1. Keep fold results strict. Close LANGUAGE.md's "What's next" item. In
   "Loops", say how to write a top-down fold (a fold whose value is a
   function, or recursion on the rest), with queens' `safe` as the example.
2. Build nothing now. Two things would be signs to revisit:
   - an example whose fold arms perform an ordered world effect, where the
     bottom-up order is wrong and a fold to a function would read badly;
   - a measured cost from a pure fold that computes results it never
     uses, which scalar.ts's used-once rule misses.

   Either one becomes a new row. The smallest step there would be a hint,
   not new semantics: the editor would say when a fold's arm prints or
   writes before it uses its result ("this runs children first; a fold to
   a function runs top-down").
