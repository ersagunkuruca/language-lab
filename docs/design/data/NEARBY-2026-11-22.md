# Things near each other as a job with several ways (design note, 2026-11-22)

BACKLOG L280g. The choices note (CHOICES-2026-11-20.md) lists spatial
partitioning as an algorithm choice: "nearby pairs by a grid or a tree
instead of all pairs". Today a program that needs it writes the grid by
hand. flock-page keeps `empty grid`, `cell of`, `cell key`, `around cells`,
`wrapped cell` and `cell size` (ten definitions) so that each of 2,000 birds
reads only the birds in its own cell and the 26 around it. The grid is a
schedule decision written as code, which the choices note's rule 5 says
code shouldn't do.

## The job

One std function, generic over any record of Float64s (the vectors
module's points, so 2D and 3D alike):

```
near : (List a, (a) -> p, Float64) -> List (List Int)
near(items, place, r)
```

For each item, the positions in `items` of the other items whose places
are within `r` of its place. In each list the positions are in order,
smallest first. Its meaning is the plain version: every pair compared.

```
near(items, place, r) = map(positions(items), (i) →
  keep(positions(items), (j) → j ≠ i and distance(place(item at(items, i)), place(item at(items, j))) ≤ r))
```

flock's `ticked` becomes `let close = near(birds, position, 10)` and
`flown(bird, birds, close at i)`. Its ten grid definitions go away.

## Its ways (the choices' algorithm kind)

| Way | Cost per call | Parameter |
| --- | --- | --- |
| all pairs (the meaning) | n² | none |
| uniform grid | n · k, k the items within r on average | cell size, `r` unless held |
| k-d tree | n log n + n · k | leaf size (8) |

The choices file gets one entry for each call main reaches:

```
<call> way: ticked's near: grid of r cells; among all pairs, grid, k-d tree; target JavaScript
```

A person can hold the way (`held … : k-d tree`) or the cell size
(`grid of 5 cells`), as with L280e's parameters. Measured sizes (L280d)
give n. A grid wins once n is past a few dozen. A tree wins where the items
cluster, which only a measured run can tell.

## Why a function of the whole list, not a query

A query (`near(index, p, r)`) needs a value for the index, a type whose
representation is the grid or tree: a collection type of its own, like Set.
The whole-list job does without one. It builds the grid inside the call
and throws it away, and that is what every program written so far does: it
rebuilds the grid each tick because everything moved. A query type can come
later on top of the same ways, if a program keeps its points still between
queries.

## What it takes

1. std `near` with its meaning (the code above), its law test against
   the meaning, and the evaluator running the meaning.
2. The grid and the tree as host ways in branches-rt and the C runtime,
   both giving exactly the meaning's lists (same order, ties at `r`
   included, `≤`).
3. The choices entry, held and tuned, and the chooser's pick from n.
4. flock-page and compiler/gaps/flock rewritten onto it, the output the
   same.

## Prior art

Uniform grids for fixed-radius neighbours (Bentley, Stanat and Williams,
"The complexity of finding fixed-radius near neighbors", 1977); k-d trees
(Bentley, 1975); Halide's split of algorithm and schedule, as in the
choices note.
