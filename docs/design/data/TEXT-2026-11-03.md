# Text: equality, case, graphemes and order (L185)

Decisions, 2026-11-03. BACKLOG L185, from BLIND-SPOTS-2026-11-03 §4. It
closes SPEC S7.

## Where this stands

Text is a sequence of Unicode code points (SPEC §2.5). `length` and
`characters` count code points, and equality and `compare` compare them.
`lowercase` and `uppercase` change only A to Z. There is no normalisation
and no grapheme clusters.

## The decisions

### 1. Equality stays code points; text is NFC where it enters

Two Texts are equal when their code points are. That keeps equality cheap,
the same on every target, and the same as a hash key's.

To make that the equality people expect, **text is put in Unicode
Normalization Form C where it enters a program from the world**: `read
file`, `fetch text`, what a page's text field gives, what `read line` reads,
and a literal the editor or the text view stores. So "é" typed as one code
point and as "e" with a combining accent arrive as the same Text, and they
are the same map key.

Text a program builds itself is not normalised again: `"e" ++ "́"` is
two code points and is not equal to "é". This is rare, cheap to fix where
it happens, and the alternative (every `++` and `equal` normalising, as
Swift's `==` does) costs every program. A program that builds text from
pieces and compares it gets `normalized(t)` (NFC) to call.

Why decide now: normalising later changes what stored keys mean, which is a
migration of the user's data (BLIND-SPOTS's "cost of waiting").

### 2. Case mapping takes the language as an argument

Upper and lower case depend on the language: in Turkish and Azeri `i`
goes up to `İ` and `ı` to `I`, and the language is named in Turkish. A
function that read the machine's locale behind the program's back would be
an effect that its type doesn't show.

- `uppercase(text, in: locale)` and `lowercase(text, in: locale)` take a
  `Locale`, a std type holding a BCP 47 tag (`tr`, `en-GB`). They are pure:
  the same text in the same language gives the same answer.
- The user's own locale is a world effect, read like the time: `my
  locale()`, with a handler that a test can answer.
- Today's A-to-Z versions are right for identifiers, hex and protocols and
  wrong for people's text (`i` to `I` is wrong in Turkish), so they become
  `ascii uppercase` and `ascii lowercase`. A saved program keeps working,
  since the ids don't change (L184), only the names.

### 3. Graphemes beside characters

`graphemes(t)` gives the extended grapheme clusters (UAX #29), each as a
Text: a flag, an emoji with a skin tone, or "e" with its accent is one. It
sits beside `characters(t)`, which stays code points. Cutting text for a
screen (`take`, padding, a cursor) is done on graphemes.

`length` stays code points, because it is what slicing counts. A
`grapheme count` is a separate name, so nobody gets one when they meant
the other.

### 4. Order for people is a separate order

`compare` and `<` on Text stay code-point order: the structural order maps,
sets and `sort` use (L66, SPEC §2.7), the same on every machine.

Sorting names for a person uses a **collation**: `collated(locale)` gives
an order, `(Text, Text) → Order`, by the Unicode Collation Algorithm with
CLDR's tailoring for that language (Turkish puts ç after c and ğ after g).
`sort by` takes it like any other order. It never changes `compare`.

### 5. The Unicode version belongs to std's version

Normalisation, case, grapheme and collation tables change between Unicode
versions. The version is part of std's version (SHARING.md, L109), so a
program's meaning doesn't move when a host's ICU does.

## How each target does it

The evaluator and compiled JS use the host: `String.prototype.normalize`,
`toLocaleUpperCase(tag)`, `Intl.Segmenter`, `Intl.Collator`. WASM and C
need the tables. The plan there is the library's own code with the
Unicode data as a generated table (in the spirit of
MATHEMATICS-AS-LIBRARIES: written once in Ters, checked against the host
on JS), not a dependency on ICU. Shaders don't take Text.
Since C151, C's NFC at the border is UAX #15 in C with its tables read
off the compiling Node's `normalize` (compiler/src/c-nfc.ts), so it
agrees with the evaluator on the same Unicode version; WASM's host
normalises for it.

## Steps

Row L214, one PR each: (a) NFC at the world's border and `normalized`,
with SPEC §2.5; (b) `Locale`, the locale-taking case mapping, `my locale`,
and the ASCII ones renamed; (c) `graphemes` and `grapheme count`;
(d) `collated(locale)`. (a) goes first, for the reason in §1.
