## In one paragraph

A program is two files: what it computes, and its choices, how it is
stored and computed and where and in what order it runs. The compiler
fills the choices from the code and from runs it measured. Each entry
chooses among implementations that share one meaning, checked by the laws
tests already run, so a person tuning one can make a program slower but
never wrong.

## Four kinds of choice

| Kind | What it decides | Examples | Today |
| --- | --- | --- | --- |
| Representation | how a value is stored | Map as tree or hash table, List as array, records as structs of arrays (columns), pooled records on a free list | chosen by cost (represented.ts, library-reps.ts, columns.ts); Pool written in the code |
| Algorithm | which computation gives a job's answer | sin by polar (ways), a relation's mode plan, nearby pairs by a grid or a tree instead of all pairs | ways and mode plans chosen by cost (WAYS.md, modes.ts); partitioning written by hand |
| Placement | where work runs | main thread, workers, C threads, the GPU | chosen by cost (C61) |
| Schedule | the order and grouping of work | chunk sizes, tiling, fusing loops, interleaved search order | partly chosen (fusion, fold chunks); search order fixed as interleaved (2026-11-12) |

Every kind can carry parameters: a grid's cell size, a chunk size, a
worker count. The schedule kind is the one Halide (Ragan-Kelley, Adams et
al., 2013) separates from its algorithm; this note keeps Halide's split
and widens it to the other three kinds.

Pool and spatial partitioning first have to be written as implementations
of a job, each with a meaning, so they can be chosen like a Map's tree or
hash table: a pooled collection means the List or Map it stands for, and
nearby pairs by a grid mean the pairs found by comparing every two. That
is the work of L280f and L280g.

## The rules

1. **Meaning kept.** An entry names one of the implementations of the
   same job, all with the same `meaning`. The compiler refuses any other
   entry. The laws tests (L108d) already check each implementation
   against its meaning.
2. **The compiler's entries are redone when stale.** Each keeps beside its
   pick the facts it read (the type, the jobs reached, which run in loops,
   the candidates' hashes, the target, measured sizes). If those change,
   the pick is made again. So without held entries, the output depends
   only on the program and its measurements.
3. **A held entry stays.** An entry a person changed or held is kept as
   written. When the compiler would now pick another, it says so, as a
   warning beside the entry. It doesn't change it.
4. **Measurements are committed.** Sizes and call counts live in the
   choices file, so a build depends only on what is in git.
5. **The code never selects.** No pin or hint is written in the program.
   Removing the choices gives the compiler's own picks back.

## Where it lives

Beside the program: `<program>.choices`, in the saved format's style, one
entry per line, sorted by id, keyed by the type's or definition's stable
id (STABLE-REFERENCES.md), so renames and moves keep it. `ters diff` and
the editor's Changes tab show an entry's change on its own ("Map of
patients: tree to hash table"). The editor shows the choices in the
Program tab, the place E159 shows them today, and lets a person hold or
change an entry there.

A published library carries the choices for its own types and ways,
keyed by content hash (L280i, when sharing needs it).

`.lab/` keeps what only speeds the compiler up: the per-definition
summaries behind rule 2, by content hash.

## Keys and compile speed

A pick is keyed by the facts it read, not the whole program's hash. Those
facts are unions over definitions: each definition's summary (the jobs it
uses on each type, the calls it makes inside a loop) is kept by its
content hash. An edit redoes one summary; when the union comes out the
same, the pick is reused without running the chooser (early cutoff). "In
a loop" crosses definitions through calls, so it comes from the
summaries' call edges.

Measured on machine (L280b, 2026-11-20): of a warm choice of about
0.42 s, deciding is about 30%, rewriting onto the choice 23%, checking
the rewrite 36%. A kept pick skips the deciding only; the rest needs the
rewritten definitions and their checks kept by hash too, the same keying
that per-definition lowering needs (L266).
