# Hash keys that are data (C243)

GAPS round 19 left scan's DFA moves, a `Map (Int, Int) Int` built once and
read millions of times, in a weight-balanced tree on every target. After
C241 and C242 the tree's reads are 18.6% of native scan's instructions:
about 340 instructions a read, where a hash table's read is some 40. So a
hash table there would take about 16% off native, and C238 measured about
4% on core.

## Why it isn't one

The chooser (library-reps.ts `choiceOf`) picks one representation per
type for the whole program. A hash table is a choice for `Map` only where
every Map's key is hashable (`inPlace`): an Int, a Text, or a tuple or
record of them (C63f, C63g, C63k). scan also maps each set of NFA states
to its DFA state, a `Map (Set Int) Int`, and Moore's refinement keys
blocks by their signatures, a `Map (List Int) Int`. Those keys aren't
hashable, so every Map of the program stays a tree.

Letting those keys through (an experiment that skipped the check) makes
the chooser pick "Map as hash table", with Set kept as written. Lowering
then refuses, because the tables of C and WebAssembly (scalar.ts) take
only Int, Text and record keys.

## What a hashable key is

A key is hashable when its type, as stored, is Int, Text, or a record or
a data type all of whose fields are. That includes `List Int`,
`Set Int` as written (its items, a sorted list: one spelling per set,
std.ts) and `Optional (Int, Text)`. It excludes:

- a Float64, which nothing fixes as a key;
- a function;
- a Map or a Set stored as a hash table, which has no one spelling to hash.

A key holding one of these keeps the tree. Since Set is chosen before Map
is looked at, a key's Set is a hash set only if the chooser made Sets
hash sets, and then it isn't hashable. In scan, Set stays as written.

The language already says what such keys mean: Maps and Sets are ordinary
data with one spelling (std.ts, L65), so `equal`, `compare` and a hash
need no special case. A data key is hashed, compared for equality and
ordered by its structure:

- first its case, in the order the type lists them;
- then its fields, in order.

That is compare's order for data, so a table's entries, sorted when they
are listed, come out as the tree's would.

## Per target

Each target says whether it takes data keys (`dataKeys`, passed to the
chooser as `tables` and `hostMaps` are). A target that doesn't keeps the
tree, as now, so each step lands on its own.

1. **JavaScript (the evaluator and the core IR).** std.ts holds a key
   by its spelling. A spelling of data says its fields but not its case,
   so two cases with no fields would spell alike. The case's tag goes in
   front for any value that isn't a tuple. Core IR values carry `fields`
   (a getter) and `tag`, so the same spelling serves both.
2. **C.** A table's key type may be a data type, or a record holding one.
   For each such type there is a hash, an equality and a compare, walking
   the cells: the tag, then each field. The key is a counted cell, dup'd
   and dropped as a Text key is. A long list's walk goes round a loop on
   its last field rather than recursing.
3. **WebAssembly.** The same three walks over the GC structs
   (wasm-table.ts `leaves`, which now flattens records only, gets a
   data case).

## Measuring

The test for each step is scan on that target:

- its output must be unchanged;
- the chosen row is "Map as hash table";
- the time at 8000 lines goes in GAPS round 19.

Each step's own tests cover a key of each kind: a list of Ints, a Set as
written, a data type with two cases that have no fields, and a record
holding a list.
