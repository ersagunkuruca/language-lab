## In one paragraph

A program is two files: what it computes, and its schedule, how it runs.
The schedule lists every choice the compiler makes today and a few that
programs make by hand today: a type's representation, an operation's way,
a relation's mode plans, where work runs, and their parameters. The
compiler fills it from the code and from runs it measured. Each entry
chooses among implementations that share one meaning, checked by the laws
tests already run, so a person tuning it can make a program slower but
never wrong. This is Halide's split of an algorithm from its schedule
(Ragan-Kelley, Adams et al., 2013), applied to a whole program.

## What goes in it

| Choice | Today | In the schedule |
| --- | --- | --- |
| A type's representation | chosen by cost (represented.ts, library-reps.ts) | the same pick, its parameters, held or not |
| An operation's way | chosen by cost (WAYS.md) | the same |
| A relation's mode plans | chosen per mode (modes.ts) | the same; search order stays interleaved (decided 2026-11-12) |
| Where work runs | chosen by cost (C61) | GPU, workers or main thread, per loop |
| Pooling | the program writes the Pool type | "bodies in the update loop: pooled"; the code says List or Map |
| Spatial partitioning | the program writes a grid by hand | a representation of the "pairs nearer than r" job: all pairs (its meaning), grid with a cell size, or tree |
| Measured facts | none | sizes and call counts from runs, read by the next compile |

Pool and spatial partitioning first have to become representations of a
job, each with a meaning, so they can be chosen like a Map's tree or hash
table. That is the work of L280f and L280g.

## The rules

1. **Meaning kept.** An entry names one of the implementations of the
   same job, all with the same `meaning`. The compiler refuses any other
   entry. The laws tests (L108d) already check each implementation
   against its meaning.
2. **The compiler's entries follow the cache rule.** Each keeps beside its
   pick the facts it read (the type, the jobs reached, which run in loops,
   the candidates' hashes, the target, measured sizes). If those change,
   the pick is made again. So without held entries, the output depends
   only on the program and its measurements.
3. **A held entry stays.** An entry a person changed or held is kept as
   written. When the compiler would now pick another, it says so, as a
   warning beside the entry. It doesn't change it.
4. **Measurements are committed.** Sizes and call counts live in the
   schedule file, so a build depends only on what is in git.
5. **The code never selects.** No pin or hint is written in the program.
   Removing the schedule gives the compiler's own picks back.

## Where it lives

Beside the program: `<program>.schedule`, in the saved format's style,
one entry per line, sorted by id, keyed by the type's or definition's
stable id (STABLE-REFERENCES.md), so renames and moves keep it. `ters
diff` and the editor's Changes tab show an entry's change on its own
("Map of patients: tree to hash table"). The editor shows the schedule in
the Program tab, the place E159 shows choices today, and lets a person
hold or change an entry there.

A published library carries the schedule of its own types and ways, keyed
by content hash (L280i, when sharing needs it).

`.lab/` keeps what only speeds the compiler up: the per-definition
summaries behind rule 2, by content hash.

## Keys and compile speed

A pick is keyed by the facts it read, not the whole program's hash. Those
facts are unions over definitions: each definition's summary (the jobs it
uses on each type, the calls it makes inside a loop) is kept by its
content hash. An edit redoes one summary; when the union comes out the
same, the pick is reused without running the chooser (early cutoff). "In
a loop" crosses definitions through calls, so it comes from the
summaries' call edges.

A saved pick skips deciding, not the rewrite onto it. The same summaries
are the way to key the lowering passes that read whole-program facts,
which is what stopped per-definition lowering in the redesign (L266).
