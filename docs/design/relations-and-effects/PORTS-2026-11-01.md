# One shape for inputs, results and relations (2026-11-01)

Ersagun, 2026-11-01 19:27: *"What I meant by multiple outputs for
functions isn't there at all. When I select multiple nodes and make them
into a function, if they happen to have 2 outputs, a new type for those
outputs is generated, which is fine I guess, it's the grouping of the
output type of the function, but the function also should be able to be
viewed as having multiple outputs. […] A function with multiple inputs has
a virtual type of its inputs as well, doesn't it? Like from a language
point of view those two things are equivalent, they should have been
equivalent somehow. And there are functions with variable number of
inputs. And relations are something very different somehow. I don't get
it. We need a more unified view of the language."*

This note is a design discussion, not a build. It says what is there
today, proposes one picture that covers all four questions, and ends with
the choices for Ersagun and the BACKLOG rows. Earlier notes it builds on:
[RESULTS.md](../numbers/RESULTS.md) (L95, several named results),
[POLAR.md](../numbers/POLAR.md) (L97), [MODES.md](MODES.md),
[BACKWARDS.md](../../language/BACKWARDS.md) and LANGUAGE.md's "One world".

## Short answer

Every definition is a box with **ports**. A port has a type, and its name
is presentation, like every other name. A **direction** says which ports
are given and which come out. Then:

- **A function** is a box with one declared direction: its inputs given,
  its results out.
- **A relation** is the same box with no favourite direction, or several.
  A function is a relation that comes with the direction it is usually
  used in. Every function already runs backwards (BACKWARDS.md); the only
  difference is which direction the editor draws first.
- **Several results** are several ports on the out side. Nothing more.
- **The inputs together are one value, and so are the results.** A row of
  ports is a type: the tuple of their types. `f(x, y)` and `f(p)`, where
  `p` is a tuple of an x and a y, are the same call. `a, b = f(x)` and
  `r = f(x)` are the same use, one with the tuple taken apart. A tuple of
  one is just its value, and of none is `Unit`. So every function takes
  one value and gives one value, and that value may have several parts.
  This is Standard ML's view (prior art), and it is what Ersagun's "they
  should have been equivalent" asks for: they are not just equivalent,
  they are the same thing.
- **A variable number of inputs** is a port whose type is a list, drawn as
  a row of sockets that grows by one when you wire the last.

So the four things Ersagun names are one idea: ports, grouped into tuples
by a direction.

## What is there today, and where it splits

The pieces exist, but in four shapes that don't line up:

| what | how it is stored | how many results |
|---|---|---|
| `f(x, y) = e`, and every function value (lambda) | a `lambda` with params and one body | one |
| `polar(x, y) → length, angle = …` (L95) | a `def` whose body is a `Bool` condition over all ports, with `results` naming some of them | several, but only for top-level definitions |
| an interface field with results (`polar: (length, angle) → x, y`, L97c) | a predicate's function type with `results` positions and `ports` names on the field | several |
| Make it a function on nodes with two values going out (E149) | a lambda that returns a generated `Part results` record, read by field where each value was | one record |

And two ways to use a box: `call` (the declared direction, inputs by
position) and `solve` (any direction, ports by id, results bound).

That is the "multiple outputs aren't there at all" Ersagun saw: a top-level
definition can have several results, but a function made from picked nodes
can't, so the editor makes a record type instead. The record is right as a
*grouping* (Ersagun: "it's the grouping of the output type of the
function") but wrong as the only view, and wrong to be a new named type
each time.

## The proposal

### 1. Ports and tuples

A function type lists its input ports and its result ports:

```
polar : (Float64, Float64) -[Choice]-> (Float64, Float64)
quotient and remainder : (Int, Int) -> (Int, Int)
```

`(A, B)` is the **tuple** of A and B, a built-in type like `Array`, not a
node kind and not a generated typedef. It is structural: two tuples of the
same types are the same type wherever they come from, so `Part results`,
`Part results 2`, … go away. Tuples are positional for the checker; the
names you see (`length`, `angle`) come from the definition's ports, the way
every name in the program comes from the side tables. So `polar` fits
wherever a `(Float64, Float64) -> (Float64, Float64)` is wanted, whatever
the other function called its ports.

A tuple of one is the value itself and a tuple of none is `Unit`, so the
equivalence holds with no special cases:

| written | means |
|---|---|
| `f(x, y)` | `f` given the tuple `(x, y)` |
| `f(p)`, with `p : (A, B)` and `f : (A, B) -> C` | the same call, `p` taken apart into the ports |
| `a, b = f(x)` | the result tuple taken apart, each part named |
| `r = f(x)` | the result tuple kept whole; `r.length` reads one part, named from `f`'s port |

The checker does this by treating a function's inputs as one tuple type:
unifying `(α) -> R` with `(A, B) -> R` sets `α = (A, B)`. That is why
there is no ambiguity here where Swift had one (below): a one-port
function's input is its value, never a tuple of one.

### 2. Several results, everywhere a function can be

Results stop being a feature of top-level predicates. Any function,
including one inside a body, can give several:

```
part(speed, time) → drift, drop = speed · time, ½ · g · time²
```

A body that computes its results directly is written `= e1, e2` (L95b
already reads this way); it is a function whose body gives a tuple. A body
that states a condition on its ports is a relation with a declared
direction, as polar is today. These are the two ways to write the body,
one meaning, and they relate exactly the way `f(x) = e` relates to
`f(x) → r` with the condition `r = e`. That relation already holds for one
result, so this adds no new idea.

**Make it a function** on nodes with two values going out then makes a
function with two results, drawn as a frame with two output ports, called
where it was; each value going on to where it went. The tuple is still
there, as the type of the results, and the editor can show the results as
one wire when you want them grouped (§5).

### 3. Relations are boxes without a favourite direction

LANGUAGE.md's "One world" already made a relation a function returning
`Bool`. In this picture that is read the other way: a relation is the box,
and its `Bool` is the box run with every port given ("are these four
numbers a polar pair?"). Given some ports, it gives the rest, with `Choice`
when there may be none or several (MODES.md says how many). A function is
the same box with a declared direction that the checker has shown to give
exactly one answer, so it has no `Choice` in that direction.

So a call is a use in the declared direction, and a `solve` is a use in
another direction. They are one idea stored as two node kinds. Merging
them into one node, where a use names its given ports and the rest come
out, is the end state; it touches the checker, relate.ts and all four
compilers, so it is a choice for Ersagun (question 3), and the views can be
made one first.

In the graph, every call node then works the way a relation's node already
does: click a port to make it given or produced, and the node becomes the
use in that direction. "Run it backwards" stops being a separate thing you
know about and becomes a port you click.

### 4. A variable number of inputs

Two kinds are worth telling apart:

- **Any number of the same type** (`sum(1, 2, 3)`, a page's children,
  `join all`): the port is a `List`. The editor already draws a
  `cons … nil` chain as one list node; the next step is to draw it on the
  port itself, a socket per item and an empty one at the end that adds an
  item when you wire to it (Blender's multi-input sockets, prior art). The
  text reads `sum(1, 2, 3)` for `sum([1, 2, 3])` when the list is written in
  place. No language change: a view of a list.
- **Any number of different types** (`printf`, `zip` of n lists): the port
  is a tuple of any length. The language already has the shape for this:
  `map parts` and `zip parts` take any record of Float64s part by part.
  Generalising that to "any tuple, part by part" is row polymorphism
  (Wand 1987, Rémy 1989, prior art). Nothing needs it yet, so it waits
  until a program does.

### 5. In the editor

- A tuple-typed wire can be drawn **bundled** (one thick wire, its parts
  listed on it) or **fanned out** (one wire per port). The two are the
  same program, so this is a view the user toggles on a wire or a port,
  like folding a frame. It is the gesture for "the inputs are one value":
  drag one bundled wire to a node's inputs and it fills all of them.
- **A multiple selection gets ports.** The frame drawn around picked nodes
  shows, on its left, every wire coming in and, on its right, every wire
  going out: exactly the ports Make it a function would give. Making the
  function then only names the box you were already looking at.
- Outputs and dots: CONFUSING.md item 3 ("every output is a dot") fits
  this: a result port is a dot, as an input port is.

### 6. Compiled

A tuple is a representation choice like any other (REPRESENTATIONS.md): the
compiler can pass its parts as separate arguments and return them as
separate values (WebAssembly's multi-value returns, C's out-pointers or a
small struct, JavaScript's arrays only when it must). C31 ("a recursion
that gives back a Pair returns its two fields without the record") becomes
the general rule, and C55 already drops results no caller reads.

## 7. Order and names, and hashes that ignore order (Ersagun, 19:49)

Ersagun: *"The default way to call a function and destructure its outputs
should be the ordered way, like (c,d)=f(a,b) […] but in cases where that
doesn't work, like when you are flipping the relation into a weird shape,
it could look more like named tuples. The language holds a default order
(and "polarity") for each port, and names as well, but the names are
irrelevant somehow. […] Is it possible to make it really unordered
underneath so that it helps us match the hash of functions that look
different under ordering but are the same: like f(x,y)=x*x+y*y and
g(x,y)=y*y+x*x?"* He agreed (19:51) to write it up here.

**Order by default, names when flipped.** Each port has a declared order
and a polarity (given or produced in the declared direction). Its name is
in the side tables, as every name is, so renaming never changes meaning or
hash. A use in the declared direction is positional: `c, d = f(a, b)`. A
use in another direction names its givens and binds the rest in declared
order: `a, b = f(c = 1, d = 2)` (RESULTS.md already reads polar this way).
A result kept whole is read `r.length`, which the editor resolves to "f's
port 1" when written, so the name is a handle only.

**Unordered underneath, in two parts.**

1. **Port order as a layer.** A definition's hash is taken over its body
   with its ports as a set, and the declared order is kept beside it, the
   way names are. Ports are told apart by how the body uses them: the body
   is hashed with each port numbered by its place in a canonical order of
   the body's subterms (tree canonization, as Aho, Hopcroft and Ullman's
   tree isomorphism), not by its place in the parameter list. Ports the
   body treats alike (x and y in `x·x + y·y`) tie, and either choice gives
   the same hash. So `f(x, y)` and the same body as `g(y, x)` are one
   relation with its ports in another order, and "Same as the library's"
   (E161, L126) can say "same as `magnitude` with its inputs swapped".
   Whether two definitions are the same *function* still compares the
   order too.
2. **Operands of commutative operations, sorted.** When hashing, the
   operands of an operation whose interface declares it commutative are
   sorted by their own hashes, so `x·x + y·y` and `y·y + x·x` hash the
   same. The text and graph keep what the author wrote; only the hash
   changes. Only where a law says so: Float64's `+` and `·` commute but
   don't associate, so floats get sorting only; Int and Rational also
   associate, so their sums and products are flattened before sorting
   (the laws are the interfaces' declared laws, L108d and T7). Never
   across effects: two `print`s, or a `one of` whose canonical first
   answer depends on order, keep their order. So it applies to pure parts
   only.

**What it buys.** Sharing finds more matches (L126). The compiler computes
`x·x + y·y` once where it's written both ways (common subexpressions up to
the laws, C69), test results and compiled code cached by hash (T7c) hit
more often, and evaluation order is the compiler's to choose wherever no
effect pins it. Full program equivalence is undecidable, so this catches
the shallow, common cases; equality saturation (e-graphs) is the known way
further, if ever needed.

## What this changes, and what it doesn't

- **The meaning of existing programs doesn't change.** `polar`, `sum and
  difference`, physics' `rotate` keep their meaning and their text.
- **Removed:** generated `Part results` types; the field-level `results`
  and `ports` on interface fields (they become an ordinary function type
  with a tuple of results); "only top-level definitions have results".
- **Added:** one built-in type, the tuple, and one checker rule (a
  function's inputs are one tuple). No new node kind.
- **Two Landscapes:** in the language this is the simplest form there is
  (one value in, one value out, parts named). Each target's calling
  convention is that target's business.

## Choices for Ersagun

1. **Tuples of ports.** Should a function's inputs and results each be one
   tuple, so `f(x, y)` and `f(p)` are the same call and Make it a function
   gives several results instead of a `Part results` type?
   *Recommended: yes.* **Ersagun chose yes (2026-11-01 19:35).** The alternatives were results only (inputs stay a
   list of params, no `f(p)`), or keeping today's records.
2. **Variable inputs.** A list port drawn as growing sockets now, with
   different-typed variable inputs (row polymorphism) left until a program
   needs it? *Recommended: yes.* **Ersagun chose yes (2026-11-01 19:35).**
3. **Call and solve.** Make them one node kind in the model (a use names
   its given ports), or make them one only in the views and keep two kinds
   stored? *Recommended: views first (E168), then the model merge (L130)
   as its own step after L128.* **Ersagun chose this (2026-11-01 19:36).**

## Prior art and influences

- **Standard ML** (Milner, Tofte, Harper and MacQueen, *The Definition of
  Standard ML*, 1990/1997): every function takes one argument, which may be
  a tuple, and tuples are records with numbered labels. Prior art for
  "the inputs are one value".
- **Swift's tuple splat**, removed by Swift Evolution SE-0029 (2016) and
  SE-0110 (2017): passing a tuple where a function wanted several
  parameters was ambiguous with a function of one tuple parameter and broke
  argument labels. Considered: our rule avoids both because a tuple of one
  is its value and names are presentation, not part of the type.
- **Multiple values** in Go, Lua and Common Lisp (already in RESULTS.md),
  and **WebAssembly's multi-value** proposal: results side by side.
- **Relations and modes**: Prolog, miniKanren (Friedman, Byrd and
  Kiselyov), Mercury's modes (Somogyi, Henderson and Conway, 1996),
  Modelica's acausal equations. Already credited for "a function is a
  relation"; here they are prior art for "a direction is a choice of given
  ports".
- **The category of relations** (Rel), where any input can be bent into an
  output, and string diagrams that draw this: influence on "inputs and
  results are the same kind of thing".
- **Row polymorphism** (Mitchell Wand, 1987; Didier Rémy, 1989): prior art
  for functions over tuples of any length, if L129 is ever built.
- **Hashing up to order**: tree canonization (Aho, Hopcroft and Ullman,
  *The Design and Analysis of Computer Algorithms*, 1974) and canonical
  labelling of graphs (Brendan McKay's nauty) for ports as a set; matching
  modulo associativity and commutativity in Maude (Clavel, Eker, Meseguer
  and others) and term rewriting for sorted operands; equality saturation
  with e-graphs (egg, Willsey, Nandi, Wang, Flatt, Tatlock and
  Panchekha, POPL 2021) as the way further. Unison's content hashing is
  already credited for hashing by content. All prior art.
- **Blender's multi-input sockets** (geometry nodes, Join Geometry):
  prior art for a port that takes any number of wires.
- **Hardware description languages** (Verilog, VHDL): a block with named
  input and output ports, already credited in RESULTS.md.
